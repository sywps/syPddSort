# 像素拼图异步 PvP 与机器人训练数据项目计划

版本：v1.0（已按玩法定稿更新）  
日期：2026-09-03  
目标工程：`game-pdd-v2`（Cocos Creator 3.8.8 + 微信 CloudBase）

## 1. 项目目标

在现有像素拼图/PCH 玩法上增加异步 PvP：两名玩家不必同时在线，各自在相同的关卡与规则条件下完成挑战，由服务端验证过程并结算胜负；同时支持局中断点恢复，并将真实玩家的合法操作轨迹沉淀为可复现、可脱敏、可版本化的机器人训练数据。

项目不是简单增加一个排行榜，而是建立四个闭环：

1. 对战闭环：匹配/挑战 → 开局 → 保存 → 恢复 → 完成 → 校验 → 结算 → 战绩。
2. 数据闭环：动作采集 → 完整性校验 → 脱敏 → 数据集构建 → 质量报告。
3. 机器人闭环：基线策略 → 离线训练 → 固定题库评测 → 灰度部署 → 表现监控。
4. 运营闭环：赛季/分段 → 任务与奖励 → 风控 → 指标分析 → 参数调整。

## 2. 已确认产品基线与待确认事项

以下玩法基线已经确认；隐私授权、数据保留期及机器人对排位分的权重仍需在里程碑 M0 评审中确认：

| 议题 | 推荐默认值 | 需要确认的原因 |
|---|---|---|
| 对战形式 | 同一不可变关卡快照，各自独立作答 | 最适合异步、重放和公平校验 |
| 对手来源 | 好友挑战、已验证真人历史成绩、机器人补位 | 普通排位必须先搜索合格真人 replay，候选为空才允许机器人补位 |
| 对局时限 | 使用同一关卡倒计时；好友挑战另设接受截止时间 | 对局内结果必须基于同一虚拟时间轴比较 |
| 胜负主规则 | 谁先通关谁赢；尚无人通关时谁先失败谁输；倒计时结束比较完成进度 | 已由玩法规则确认，服务端按终局时间轴唯一结算 |
| 道具 | 排位默认禁用；娱乐模式可使用但单独队列 | 保证训练标签和竞技公平性 |
| 广告复活 | 排位禁用；娱乐模式记录成本并单独结算 | 广告可改变时间/容量，不能混进同一公平规则 |
| 对手呈现 | 普通排位统一显示“排位对手”；好友局显示“好友挑战” | 客户端不暴露真人历史/机器人来源，服务端和内部埋点必须保留真实来源用于审计 |
| 训练授权 | 隐私说明中明确“用于玩法优化和自动对手训练”并提供退出机制 | 合规与用户信任要求 |
| 未成年人策略 | 默认不将可识别信息进入训练集，按平台要求处理退出/监护 | 需要法务和平台政策确认 |

## 3. 范围定义

### 3.1 MVP 必须包含

- 异步 PvP 首页、匹配、挑战详情、对局 HUD、结算、战绩入口。
- 同一 `levelSnapshotId + rulesVersion + seed` 的公平对局清单。
- 单设备本地即时保存、云端动作增量同步、跨启动恢复。
- 规范化动作日志、周期性检查点、状态哈希、完整回放。
- 服务端身份校验、幂等写入、顺序校验、规则重放、结果签名。
- 真人历史轨迹形成对手“幽灵结果”；规则机器人用于冷启动补位。
- 数据脱敏、同意/退出状态、训练样本构建和质量报告。
- 基础匹配分、对局历史、异常对局标记、核心运营看板。

### 3.2 MVP 明确不做

- 实时同步棋盘、WebSocket、观战和实时语音。
- 强化学习在线自我博弈、在线学习或客户端模型训练。
- 复杂公会战、多人锦标赛、实时淘汰赛。
- 跨玩法共享统一战斗通行证。
- 完全依赖模型判断作弊；规则校验必须由确定性代码完成。

### 3.3 后续版本候选

- 对手进度“幽灵条”和延迟播放，但不泄露具体解法。
- 每日擂台、赛季、连胜、好友复仇、分享挑战码。
- 不同风格机器人：稳健、冒险、道具型、拟人失误型。
- 模仿学习、价值网络、搜索策略、难度自适应机器人。
- 关卡质量预测、死局预警与智能提示生成。

## 4. 核心玩法设计

### 4.1 推荐对局模型

每场比赛生成不可变的 `matchManifest`：

- `matchId`：全局唯一。
- `mode`：`ranked` / `casual` / `friend` / `bot_training`。
- `levelSnapshotId`：关卡内容快照，而非可变的逻辑关卡号。
- `levelContentHash`：规范化关卡 JSON 的 SHA-256。
- `rulesVersion`：PCH 规则版本。
- `schemaVersion`：动作/快照协议版本。
- `seed`：所有随机选择的确定性种子。
- `allowedProps`、`revivePolicy`、`timeLimitMs`。
- `acceptDeadline`、`finishDeadline`。
- 两个参赛席位及其公开身份快照。

双方都从同一清单开始，彼此不共享实时状态。第一名玩家完成后，提交的已验证结果成为待挑战成绩；第二名完成后服务端统一结算。

### 4.2 对手形态

1. 已完成真人：立即匹配历史上同等级、同关卡池的合法成绩，体验最快。
2. 开放挑战真人：A 先玩，B 在截止时间前应战；适合好友挑战。
3. 机器人：无合适真人时补位，使用同一清单预先生成经过验证的轨迹和成绩。

不得把普通排行榜分数直接伪装成对手过程。对手结果必须绑定可验证的 replay 或机器人策略版本。

所有形态都是严格异步：当前玩家进入关卡之前，对手轨迹已经完成并冻结。服务端不转发正在游戏的另一名玩家 checkpoint，客户端不建立 WebSocket、不轮询对手局中进度，也不显示实时在线状态。

### 4.3 推荐胜负规则

服务端按两条独立时间轴确定唯一结果：

1. 双方都通关：通关时间更早者获胜。
2. 只有一方通关：通关方获胜。
3. 尚无人通关而一方先失败：先失败者落败。
4. 双方都失败：失败时间更晚者获胜。
5. 倒计时结束仍无终局：先比较完成进度；相同进度和相同终局时间为平局。

排位禁用道具、广告复活、广告加时和广告扩容；保留原倍速按钮，所有玩家都可自由切换。比赛用真实经过时间结算，不按倍率折算计时，因此不把付费能力加入胜负比较。

### 4.4 状态机

```text
普通排位：MATCHED_FROZEN → IN_PROGRESS → SUBMITTED → VERIFYING → SETTLED
好友发起：PLAYING_CREATOR → SUBMITTED → VERIFYING → WAITING_OPPONENT
好友应战：WAITING_OPPONENT → PLAYING_CHALLENGER → SUBMITTED → VERIFYING → SETTLED
本人中断：IN_PROGRESS → PAUSED → IN_PROGRESS
校验失败：VERIFYING → REJECTED_CORRUPT / REJECTED_ILLEGAL
任意未完成态 + 截止 → EXPIRED / FORFEIT
SETTLED → REWARDED → ARCHIVED
```

所有迁移由服务端检查当前版本，使用条件更新，避免重复提交、重复结算或重复发奖。

## 5. 客户端架构改造

### 5.1 分层原则

- `PchConveyorRules`：纯规则和确定性状态迁移，不访问 UI、时间、网络或随机全局变量。
- `PvpCommandAdapter`：把 UI 意图转成规范命令，并调用规则层。
- `PvpMatchSession`：维护序号、时钟、保存状态、同步队列和生命周期。
- `PvpCloudGateway`：只负责 CloudBase API、重试、幂等和错误显化。
- `PvpReplayPlayer`：从初始清单重放命令并验证哈希。
- UI 控制器：只展示会话状态，不直接修改规则数据。

### 5.2 规则层先决改造

当前权威状态不仅包含 `BoardModel.currentColors/locked`，还包含入口队列、ready 数量、载位栈、容量等。应新增受控接口：

- `exportState(): PchRulesSnapshot`
- `importState(snapshot): void` 或 `fromSnapshot(level, snapshot)`
- `applyCommand(command): CommandResult`
- `computeStateHash(): string`
- `validateInvariants(): void`

快照不得通过 `as any` 直接修改 private 字段。恢复后必须检查：豆豆守恒、队列 ready 范围、载位层数、锁定状态与正确颜色一致性、容量为 3 的倍数、有效格数量一致。

### 5.3 规范命令

MVP 建议只记录能改变权威状态的业务命令：

```ts
type PvpCommand =
  | { type: 'SELECT_BLOCK'; row: number; col: number }
  | { type: 'USE_BRUSH' }
  | { type: 'USE_MAGNET'; colorId?: number }
  | { type: 'USE_FREEZE' }
  | { type: 'EXPAND_CAPACITY'; grantId: string }
  | { type: 'PAUSE'; reason: 'app_hide' | 'system' }
  | { type: 'RESUME' }
  | { type: 'FORFEIT' };
```

传送带推进、入队转移、自动归位等由确定性模拟根据命令和逻辑 tick 推导，不记录每帧坐标。动画事件不能成为胜负规则输入。

每条动作包含 `matchId, participantId, seq, actionId, clientElapsedMs, logicalTick, command, preStateHash, postStateHash, clientBuildId, createdAtClient`。服务端补充接收时间和校验结果。

### 5.4 时间与随机性

- 竞技时间使用服务端发放的开始/截止信息，客户端只展示和记录活跃区间。
- app hide、广告、系统中断必须形成可审核暂停区间；是否暂停计时由模式规则决定。
- 禁止业务逻辑使用裸 `Math.random()`；统一使用 `seed + rngStep` 的确定性 RNG。
- 冻结等效果记录逻辑持续时间或逻辑 tick，不依赖设备帧率。
- 恢复时不能因离线时长重复获得冻结、广告或容量奖励。

## 6. 保存、同步与恢复

### 6.1 双层保存策略

本地层：每个已确认命令后立即更新轻量 WAL；每 5 个命令或 10 秒生成完整检查点；app hide 前强制保存。  
云端层：动作按小批次增量上传；每 20 个命令、关键道具、暂停或完成时上传检查点。

本地失败要显式阻止继续排位，避免产生无法恢复/验证的竞技过程。云端短时不可用可进入“待同步”状态，但必须设置最大未同步动作数与截止策略。

### 6.2 检查点内容

- 身份：`matchId, participantId, checkpointId, lastSeq`。
- 版本：`schemaVersion, rulesVersion, levelSnapshotId, levelContentHash, clientBuildId`。
- 棋盘：`currentColors, locked`。
- 传送带：全部 carriers、entryColors、readyEntryCount、capacity。
- 玩法：逻辑 tick、剩余时间、冻结截止 tick、道具库存/已消费 grant。
- 统计：选择数、无效操作数、暂停区间、恢复次数、死局次数。
- 完整性：`previousCheckpointHash, stateHash, commandTailHash`。

检查点不包含节点坐标、Tween、粒子、音频、临时动画对象。恢复 UI 时从权威状态重新渲染。

### 6.3 恢复流程

1. 拉取服务端 match 状态和最高已确认 `lastSeq`。
2. 读取本地检查点与 WAL。
3. 比较 `matchId/rulesVersion/level hash`；任一不一致立即停止，不做降级恢复。
4. 选择服务端确认的最新合法检查点。
5. 重放该点之后的已确认命令。
6. 对本地未确认命令按 `actionId` 幂等补传并等待确认。
7. 校验最终 state hash 和守恒不变量。
8. 重新构建视图后解锁输入。

如果哈希不一致，保留证据并进入 `RECOVERY_CONFLICT`，允许用户退出/申诉，不应悄悄使用某一份状态覆盖。

### 6.4 冲突原则

- 进度、经济等现有 `syncUserState` 可继续使用 max/merge 语义。
- 对局状态禁止字段级合并；只能按单调 `seq` 追加动作并由规则重放。
- 同一账号多设备同时操作：服务端对 participant 持有可续租 session lease；新设备接管后旧 lease 失效。
- 完成/弃权/过期后禁止继续追加会改变结果的命令。

## 7. 服务端与 CloudBase 设计

### 7.1 新增服务边界

建议独立云函数，而不是扩展现有统计函数：

- `pvpMatchmaking`：创建匹配、接受挑战、查询等待状态。
- `pvpMatchSession`：开始、心跳、暂停、恢复、接管 lease。
- `pvpAppendActions`：校验身份、顺序、大小、幂等并追加动作。
- `pvpSaveCheckpoint`：保存版本化检查点和哈希。
- `pvpSubmitRun`：封口动作流，进入验证队列。
- `pvpVerifyRun`：服务端重放、计算成绩、输出 verdict。
- `pvpSettleMatch`：事务式结算、评级、奖励和战绩。
- `pvpHistory`：分页查询公开战绩和详情。
- `pvpTrainingExport`：内部离线任务，构建脱敏训练分片。

### 7.2 推荐集合

| 集合 | 用途 | 核心索引 |
|---|---|---|
| `pvp_match` | 清单、状态、双方、结算 | `matchId unique`; `status+deadline`; `participants.openidHash` |
| `pvp_participant` | 单方会话和成绩 | `matchId+slot unique`; `playerId+createdAt` |
| `pvp_action_chunk` | 压缩后的有序动作块 | `participantId+startSeq unique` |
| `pvp_checkpoint` | 可恢复快照 | `participantId+lastSeq unique` |
| `pvp_replay_verdict` | 重放结果、异常与版本 | `participantId unique`; `verdict+createdAt` |
| `pvp_rating` | 模式/赛季评级 | `seasonId+playerId unique` |
| `pvp_reward_ledger` | 幂等奖励账本 | `settlementId+rewardType unique` |
| `pvp_consent` | 数据授权版本与退出 | `playerId+purpose unique` |
| `ml_trajectory_manifest` | 脱敏样本元数据 | `datasetVersion+sampleId unique` |

原始动作可按 20–50 条组成 chunk，避免一动作一文档产生高费用。单请求限制动作数、压缩后字节数和命令字段白名单。

### 7.3 API 通用要求

- 玩家身份只能取 `cloud.getWXContext().OPENID`，不得信任 event 中的 openid。
- 所有写请求包含 `requestId`，服务端维护幂等结果。
- 所有响应返回 `serverTime, matchVersion, acceptedSeq, state`。
- 非法状态迁移返回稳定 error code，例如 `PVP_MATCH_CLOSED`，不能只返回自由文本。
- 核心集合缺失、版本不支持或哈希不一致时 fail fast。
- 日志禁止输出 openid、token、完整动作载荷和用户可识别资料。
- 结算、评级、奖励必须在事务或幂等账本保护下执行。

## 8. 训练数据体系

### 8.1 数据分层

1. L0 原始运营数据：动作 chunk、检查点、服务端时间和校验记录；权限最严，有限期保留。
2. L1 合法回放：只保留能够从初始清单完整重放且终态哈希一致的轨迹。
3. L2 脱敏轨迹：移除 openid、昵称、头像、网络/设备精细标识，换成数据集内随机主体 ID。
4. L3 训练样本：`observation → action → nextObservation → reward/done`。
5. L4 评测集：固定关卡、固定种子、固定难度分桶，严格禁止进入训练集。

普通 `user_behavior` 和 `level_record` 只用于产品指标或轨迹标签补充，不能替代动作序列。

### 8.2 Observation 设计

建议首版使用结构化状态，不使用屏幕截图：

- 棋盘正确色、当前色、锁定 mask、有效格 mask。
- 每个载位三层颜色与相对出口位置。
- 入口队列及 ready 边界。
- 剩余时间、容量、合法道具、当前逻辑 tick。
- 每种颜色未完成目标数、缓冲区颜色计数。
- 上一步动作、最近 N 步摘要。
- `levelSnapshotId/rulesVersion` 只作上下文，不把玩家身份作为特征。

状态必须从规则快照确定性生成，不能采集视图节点和像素坐标作为权威输入。

### 8.3 Action 与标签

- 主动作标签使用规范命令及参数，如 `SELECT_BLOCK(row,col)`。
- 保存动作执行前的合法动作 mask，训练时避免学习非法点击。
- 记录规则返回的实际移动格、颜色、缓冲变化，但作为结果特征而非客户端声明。
- 无效点击可进入独立行为分析集；默认不作为专家模仿目标。
- 道具/复活轨迹单独标记，排位无道具模型不混用。

### 8.4 Reward 建议

首版离线奖励由确定性代码计算：

```text
+1.0  每新增一个正确锁定像素
-0.02 每次选择
-0.10 非法/无效选择
-0.05 每增加一个长期占用缓冲的豆豆
-1.00 进入确定性死局
+5.00 通关
-2.00 超时或缓冲满失败
```

奖励仅用于训练，竞技结算继续使用独立 `performanceTuple`，避免模型奖励调整改变历史胜负。

### 8.5 样本过滤与质量门槛

只有同时满足以下条件的轨迹进入主训练集：

- 用户对该用途处于有效授权状态，且未被删除请求命中。
- 服务端重放 verdict 为 `VALID`。
- 初始/终态和所有采样点哈希一致。
- 关卡快照、规则版本和 schema 可解析。
- 动作序号连续，时间非负，豆豆数量守恒。
- 无已确认作弊、调试构建、外部关卡预览、自动化 QA 标记。
- 达到最低有效动作数；挂机、崩溃、纯无效点击单独分桶。

按玩家而不是按轨迹做 train/validation/test 切分，防止同一玩家操作风格泄漏到评测集。按关卡难度、结果、水平、客户端版本和模式做分层抽样。

### 8.6 隐私、保留和删除

- 保存授权文本版本、时间、用途和撤回时间。
- 原始 operational 数据建议 30–90 天；脱敏合格轨迹按批准策略保留。
- 建立 `subjectDeletionTombstone`，在下一次数据集构建时排除并重建受影响分片。
- 数据集 manifest 记录来源时间窗、过滤规则、样本量、哈希、构建代码版本。
- 训练人员只访问脱敏层；生产 openid 映射不进入训练环境。
- 上线前由法务/隐私负责人审核微信平台规则、隐私说明与未成年人处理。

## 9. 机器人路线

### 9.1 R0：规则基线机器人（MVP）

使用纯规则评分选择下一步：优先能立即归位的连通块，最小化新增长期缓冲，避免填满关键载位，必要时使用有限深度搜索。加入可配置思考延迟和受控次优选择形成不同强度。

成功标准：100% 生成协议合法轨迹；固定题库无崩溃/不变量破坏；可通过服务端同一验证器；强度可由参数单调调节。

### 9.2 R1：行为克隆

使用高质量真人轨迹训练结构化策略模型，输入 observation + legal mask，输出规范动作分布。训练离线进行，模型必须与数据集版本、代码 commit、超参数和评测报告绑定。

门槛：相比规则机器人，在保留集上提高通关率或降低成本；非法动作率在 mask 后为 0；不同尺寸/难度分桶无严重回退。

### 9.3 R2：价值模型与搜索

训练状态价值/动作价值模型，为 beam search 或 MCTS 提供排序。它比直接在线强化学习更可控，也能给“智能提示”和关卡难度分析复用。

### 9.4 R3：受控强化学习（后续）

仅在确定性模拟器、固定资源预算和离线评测门槛下开展。禁止生产实时自我更新；任何新模型必须先影子运行、再小流量、可即时回滚。

### 9.5 机器人在线服务

MVP 优先离线预生成机器人 replay 池，按关卡、强度、规则版本缓存；匹配时选取合适轨迹，成本和稳定性优于实时推理。只有个性化策略确有收益后才建设在线推理函数。

机器人记录 `botPolicyId, policyVersion, configHash, modelVersion?, generationSeed`，确保对局可重现。

## 10. 匹配、评级与经济

### 10.1 匹配

- 以模式、规则版本、关卡池、评级区间、最近对手去重为主要条件。
- 严格按 MMR ±75、±125、±200 三档搜索合法真人成绩池；全部窗口均无合格候选时才允许机器人补位。
- 历史真人 replay 只能在隐私和反重复策略允许时作为异步对手。
- 不同关卡不能直接用完成时间比较，必须由同一 match manifest 保证同题。

### 10.2 评级

可见段位采用王者体系：倔强青铜、秩序白银、荣耀黄金、尊贵铂金、永恒钻石、至尊星耀、最强王者，并按王者星级继续细分非凡、无双、绝世、至圣、荣耀、传奇王者。后台隐藏 MMR 负责匹配，前 5 局为定位赛，之后按局数和分段调整 K 值；胜 +1 星、负 -1 星、平局不变。机器人补位局影响排位分的具体权重仍需运营评审冻结。

### 10.3 奖励

- 发奖只读取 `SETTLED` 且有合法 verdict 的结果。
- 每份奖励写入幂等 ledger；重复调用返回相同结果。
- 客户端只展示服务端账本结果，不自行增加货币/道具。
- 断线、过期、弃权和校验失败的补偿规则在上线前配置化。

## 11. 反作弊与数据可信度

### 11.1 确定性硬校验

- 初始关卡 hash、规则版本、seed 必须匹配清单。
- seq 连续且 actionId 唯一；命令类型与参数在白名单。
- 每步通过服务端规则 reducer，非法命令直接标记。
- 检查豆豆总量、载位深度、ready 数、锁定正确性、时间单调性。
- 完成状态由服务端推导，客户端 `win/score` 只作提示。
- 道具必须引用已发放且未消费的 grantId。

### 11.2 软风险信号

- 不可能的持续操作频率、完全一致的机械间隔。
- 同设备/账号异常并发、频繁 lease 抢占。
- 大量 hash 冲突、恢复冲突或截止前集中提交。
- 与已知脚本轨迹高度重复。

软风险只用于排队复核、降低训练权重或延迟奖励；封禁必须有清晰规则和申诉路径，不交给黑盒模型单独决定。

## 12. UI/UX 计划

### 12.1 页面与组件

- PvP 大厅：排位/娱乐/好友挑战、评级、赛季、最近战绩。
- 匹配页：预计等待、取消和统一的“正在匹配实力相当的对手”反馈，不显示补位来源。
- 挑战卡：对手公开资料快照、关卡、规则和截止时间；普通排位不展示内部来源。
- 对局 HUD：左侧对手身份与真实棋盘缩略图、双方进度、剩余时间、保存/同步状态和网络异常。
- 恢复弹窗：上次保存时间、已同步序号、冲突/过期说明。
- 结算页：胜负、比较维度、评级变化、回放摘要、再战。
- 战绩页：分页、模式筛选、结果、异常处理中状态。

### 12.2 体验约束

- PvP HUD 不遮挡棋盘、传送带、道具和主要操作区。
- 正常保存不弹 Toast；只用轻量状态图标。无法安全保存时明确阻止继续。
- 对手缩略图只显示其在当前虚拟时间已经锁定的真实格子；真人来自 `boardTimeline`，机器人来自开局冻结轨迹，不允许按百分比猜测棋盘。
- “对手离线”不是错误；异步模式文案要建立正确预期。
- 普通排位的真人历史对手和机器人补位共用玩家式昵称、头像、段位与“排位对手”标签；不得显示机器人脸、AI 文案或 AI 角标，也不得伪造“实时在线”状态。
- 主线和 PvP 会话彻底隔离，退出 PvP 不改变主线局中状态。

## 13. 可观测性与指标

### 13.1 北极星与漏斗

- 北极星：每周完成且通过验证的 PvP 对局用户数。
- 漏斗：大厅曝光 → 发起匹配 → 找到对手 → 开局 → 提交 → 验证通过 → 结算 → 再战。
- 体验：匹配 P50/P95、恢复成功率、动作同步延迟、验证时长、结算时长。
- 质量：合法回放率、hash 冲突率、过期率、弃权率、跨设备冲突率。
- 公平：先后手胜率、不同设备/网络/关卡/道具策略的胜率差。
- 机器人：补位率、识别后退出率、各强度胜率、重复对手率、投诉率。
- 数据：授权率、可训练轨迹率、过滤原因分布、版本覆盖、数据漂移。

### 13.2 告警

- 合法回放率或结算成功率低于阈值。
- 某 clientBuildId 的 hash 冲突突然上升。
- 云函数错误、延迟、集合写入或费用异常。
- 单关卡胜率、死局率、未完成率突变。
- 机器人胜率偏离目标区间或模型非法输出非零。

## 14. 工作分解（Epics）

### E0 产品与协议冻结（1 周）

- 固化已确认的模式、胜负、排位禁用项、时限、普通排位统一呈现规则，并评审隐私授权。
- 编写 match/participant/action/checkpoint/verdict 状态机和 JSON Schema。
- 给 `rulesVersion, schemaVersion, levelSnapshotId` 制定兼容策略。
- 产出威胁模型、数据保留表、MVP 埋点字典。
- 验收：产品、客户端、服务端、算法、QA、数据、法务共同签字。

### E1 确定性规则与回放内核（2–3 周）

- 从 UI 控制器抽出规范 command reducer。
- 实现完整 snapshot export/import、hash、invariant。
- 替换业务裸随机为 seeded RNG。
- 建 Node 可执行的 headless replay 验证器。
- 建协议 golden fixtures 与旧版本兼容测试。
- 验收：同一 manifest + commands 在客户端和 Node 得到同一逐步 hash。

### E2 客户端 PvP 会话与恢复（2–3 周，可与 E3 后半并行）

- 实现 PvpMatchSession、WAL、checkpoint、上传队列、lease。
- 处理启动、hide/show、断网、重试、跨设备接管、过期。
- 制作大厅、匹配、HUD、恢复、结算和战绩 UI。
- 主线/PvP 上下文隔离；接入明确错误态。
- 验收：任意合法动作点杀进程后恢复到同一 state hash。

### E3 CloudBase 对局服务（3–4 周）

- 建集合、索引、权限和测试环境。
- 实现匹配、会话、动作、检查点、提交、验证、结算、历史函数。
- 建动作 chunk、请求幂等、条件更新、奖励 ledger。
- 验收：重复/乱序/越权/过期请求不会破坏状态或重复发奖。

### E4 训练数据管道（2–3 周）

- 建授权记录、脱敏映射、删除 tombstone。
- 实现 L0→L3 构建脚本、质量过滤、玩家级数据切分。
- 生成 dataset manifest、质量报告和样本浏览器。
- 验收：随机抽样可从 manifest 回溯规则版本并完整重放；训练集无 openid/昵称/头像。

### E5 基线机器人与匹配补位（2–3 周）

- 实现 heuristic + 有限搜索机器人及难度参数。
- 离线生成按版本/关卡/强度分桶的 replay 池。
- 匹配接入真人优先、全窗口无合格真人后机器人补位；客户端统一呈现“排位对手”，服务端保留真实来源。
- 验收：固定题库达到目标通关率，全部轨迹通过正式验证器。

### E6 QA、风控、灰度和运营（2–3 周）

- 完成自动化、弱网、兼容、压力、安全、隐私和经济测试。
- 建 PvP/训练数据看板、告警、开关、回滚和人工复核工具。
- 内部 → 1% → 5% → 20% → 50% → 全量灰度。
- 验收：每级门槛达标后人工批准升级；异常可关闭入口且不影响主线。

### E7 学习型机器人（MVP 后，4–8 周起）

- 行为克隆基线、模型注册、离线评测、影子运行。
- 价值模型/搜索与难度校准。
- 小流量受控替换规则机器人，保留一键回滚。

## 15. 里程碑与估算

假设团队配置：1 产品、1 UI/UX、2 客户端、2 服务端/数据、1 算法、2 QA（部分角色可兼职但周期会增长）。

| 里程碑 | 周期 | 交付 |
|---|---:|---|
| M0 方案冻结 | 第 1 周 | PRD、协议、状态机、隐私/风控边界 |
| M1 可重放内核 | 第 2–4 周 | command reducer、snapshot、hash、headless replay |
| M2 单人云恢复 | 第 4–6 周 | WAL、云同步、杀进程/跨设备恢复 |
| M3 双人闭环 | 第 6–9 周 | 匹配、提交、验证、结算、战绩 |
| M4 数据与规则机器人 | 第 8–11 周 | 脱敏数据集 v1、机器人 replay 池、补位 |
| M5 灰度上线 | 第 11–13 周 | 看板、压测、安全、灰度与回滚 |
| M6 学习机器人 | 上线后 4–8+ 周 | BC/价值模型、影子评测、小流量部署 |

MVP 合理估计为 11–13 周；若只有 1 客户端 + 1 服务端，建议按 16–20 周规划。估算不含重大规则重构、法务审批等待和新增美术外包周期。

## 16. 测试与验收矩阵

### 16.1 规则/回放

- 每种命令成功、失败、边界参数测试。
- 随机生成上万条合法/非法命令，验证守恒不变量。
- 客户端与 Node 逐步 hash parity。
- 不同帧率、动画开关、前后台切换不改变规则终态。
- 历史 rulesVersion golden replay 永久回归。

### 16.2 保存恢复

- 每个命令前后杀进程；上传中断；checkpoint 写入中断。
- 无网 30 秒、弱网、重复包、乱序包、丢包、超时。
- 本地旧/云端新、本地新/云端旧、hash 冲突。
- 多设备同时进入、lease 过期、强制接管。
- 冻结、道具飞行、入口队列、自动归位、结算临界点恢复。

### 16.3 服务端与安全

- 伪造 openid、他人 matchId、越权 participantId。
- 重复结算/发奖、并发提交、截止后提交。
- 超大 payload、未知字段、非法版本、恶意序号。
- 云函数/数据库超时与部分成功的补偿。
- 日志脱敏和最小权限审计。

### 16.4 用户可见验收

- 微信真机前 100 个目标 PvP 关卡布局无棋盘/传送带/HUD 遮挡。
- 720×1280 及代表性长短屏点击映射正确。
- 冷启动、热启动、断网、恢复、过期文案可理解。
- 普通排位来源呈现一致，好友身份、模式道具规则和胜负比较清晰；真实来源可在服务端审计。
- 主线存档、经济、图鉴和现有排行榜无回归。

### 16.5 数据/机器人

- 数据集 schema、脱敏扫描、删除重建、切分无泄漏。
- 任意样本均可重放并复算 observation/action/reward。
- 固定评测集与训练集按玩家/关卡策略隔离。
- 机器人合法动作率、通关率、成本、耗时和强度单调性。

## 17. 灰度、开关与回滚

必须支持服务端远程开关：PvP 总入口、各模式、真人匹配、机器人补位、评级、奖励、训练采集、特定 rulesVersion/clientBuildId。

回滚顺序：停止新匹配 → 允许已开局对局提交 → 暂停评级/发奖并保留 ledger → 固化原始动作证据 → 修复后重放验证 → 补结算。绝不能通过删除异常对局掩盖问题。

客户端版本不再兼容时，只允许完成旧局或提示升级；不得用新规则解释旧动作。服务端至少保留当前和上一稳定 rulesVersion 的验证能力，历史更老版本通过归档验证器离线处理。

## 18. 主要风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 动画与规则耦合导致不可重放 | 胜负和训练数据不可信 | 先完成纯 reducer 和双端 hash parity |
| 私有队列状态快照不完整 | 恢复后错局/豆豆丢失 | 正式 export/import + invariant，不直接改 private 字段 |
| CloudBase 文档写放大 | 成本和延迟失控 | action chunk、压缩、检查点节流、容量压测 |
| 客户端伪造成绩 | 竞技崩坏 | 服务端重放，客户端分数不可信 |
| 老版本关卡变化 | 历史对局无法验证 | immutable level snapshot + content hash |
| 训练数据带身份或脏轨迹 | 隐私/模型质量风险 | 分层、授权、脱敏、合法 verdict、删除重建 |
| 机器人太强或重复 | 留存下降 | 强度目标、拟人延迟、轨迹池去重、真人优先 |
| 客户端来源字段泄露或伪造在线状态 | 体验和信任风险 | UI 只消费统一对手资料；真实来源仅服务端审计；不显示“实时在线” |
| 排位道具付费优势 | 公平争议 | 排位禁用或独立队列 |
| 多设备冲突 | 状态分叉 | participant lease + 单调 seq + 冲突显化 |

## 19. 开发顺序与关键路径

关键路径是 `协议冻结 → 纯规则 reducer → 完整快照 → headless 重放 → 云端验证 → 结算`。UI、数据管道和机器人都依赖这条链，不应先用客户端上报分数临时上线。

建议最早两周做一个纵向技术样板：只支持 1 个固定关卡、无道具、单个玩家，完成 10 步动作保存、杀进程恢复、Node 重放和 hash 一致。样板通过后再扩展 UI 和匹配；若这一点做不到，应暂停完整 PvP 开发并先解耦规则层。

## 21. Definition of Done

MVP 只有同时满足以下条件才算完成：

- 两名异步参赛者能基于同一不可变清单完成并得到唯一结算。
- 任意合法中断点均可恢复，恢复终态与不中断执行的 state hash 一致。
- 服务端能拒绝伪造、乱序、非法、过期和版本不匹配动作。
- 客户端提交的分数不是权威来源；服务端能独立重放并计算结果。
- 重复请求、重复提交和重复结算不会重复发奖或修改评级。
- 机器人轨迹与真人轨迹使用同一协议和验证器；客户端普通排位呈现一致，服务端保留准确 `matchType`、策略版本和生成种子。
- 训练集只包含授权、脱敏、可重放、版本完整的数据，并支持删除重建。
- 弱网、杀进程、多设备、前后台、真机布局及前 100 个目标关卡通过验收。
- 看板、告警、远程开关、降级与回滚演练完成。
- 主线进度、现有 PCH 玩法、经济、图鉴、广告与排行榜没有用户可见回归。
