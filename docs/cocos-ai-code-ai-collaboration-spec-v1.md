# Cocos AI + Code AI 协作规范 v1

适用对象：

- Cocos Creator 项目
- AI-first 游戏开发工作流
- 以 Cocos AI 和 Code AI 为主、人类做局部修饰与最终验收的团队

本文档是一份可复用的协作规范模板，可直接用于后续 Cocos Creator 项目。

---

## 1. 目标

本规范的目标不是规定“谁来写代码”，而是规定：

1. 什么由 `Cocos AI` 负责
2. 什么由 `Code AI` 负责
3. 人工修改后，哪些字段以后不能再被 AI 覆盖
4. `scene / prefab / TS / 构建脚本 / bundle` 的边界怎么划最稳
5. 如何避免 `Code AI` 绕开 Cocos 原生体系，再造一套平行 UI 框架

一句话版：

> 静态 UI 真源在 Cocos，动态运行时真源在代码；两边都由 AI 主导生成和维护，人类只做局部修饰、纠偏和最终验收。

---

## 2. 术语定义

### 2.1 Cocos AI

`Cocos AI` 指主要负责以下内容的 AI：

- `scene`
- `prefab`
- 节点结构
- 节点层级
- 图片引用
- 基础布局
- 锚点
- 尺寸
- 视觉对齐
- 可视化预览骨架

它不是“给人拖拽用的编辑器助手”，而是：

> 负责直接生成和维护 Cocos 编辑器资产的 AI。

### 2.2 Code AI

`Code AI` 指主要负责以下内容的 AI：

- TypeScript / JavaScript 业务逻辑
- 运行时状态
- 动态 UI
- 关卡加载
- 棋盘 / 豆子 / 槽位逻辑
- 动效
- 平台适配
- 构建脚本
- bundle / CDN / 校验脚本

一句话：

> Code AI 负责游戏“活起来”的那部分。

### 2.3 Human

`Human` 指项目中的人工参与者，主要负责：

- 需求输入
- 方向判断
- 审美修正
- 局部微调
- 验收
- 风险判断

Human 不应成为重复劳动的主生产者，而应成为：

> 规则制定者、纠偏者和最终把关者。

### 2.4 Style（风格）

`Style` 指更高层的整体美术方向，例如：

- 休闲风
- 可爱风
- 动物风
- 国风

`Style` 会影响：

- 配色体系
- 材质语言
- 按钮气质
- 插画方式
- 字体感觉
- 动效节奏

一句话：

> Style 是“大方向的视觉语言”，不一定是运行时可切换的系统。

### 2.5 Skin（皮肤）

`Skin` 指在不改变玩法结构和核心交互前提下，可运行时切换的一组视觉资源包。

典型可由 `Skin` 控制的内容包括：

- 背景图
- 棋盘底图
- 格子样式
- 插槽面板图
- 棋子贴图
- 奖励特效
- 局部音效

一句话：

> Skin 是“共享骨架不变、视觉资源可换”的系统。

### 2.6 ThemeChallenge（主题挑战）

`ThemeChallenge` 指玩法内容分组或特殊关卡系统，不等于视觉皮肤系统。

例如：

- 某一组专题关卡
- 某个活动挑战页
- 某个特殊关卡合集

规则：

1. 如果项目中 `theme` 已经表示“主题挑战”，则视觉换肤系统必须改用 `skin`
2. `ThemeChallenge` 和 `Skin` 必须解耦
3. 一个挑战关卡可以套任意皮肤，一个皮肤也可以用于主关卡或挑战关卡

### 2.7 PanelSkeleton（面板骨架）

`PanelSkeleton` 指一个面板在 `scene / prefab` 中预先搭好的静态可视框架。

通常包括：

- 面板根节点
- 背景
- 标题区域
- 关闭按钮
- 内容容器
- 底部按钮区
- 默认锚点、尺寸、间距、层级

通常不包括：

- 动态文案内容
- 数字刷新
- 列表数据
- 点击后的业务逻辑
- 运行时临时特效

一句话：

> 面板骨架是“壳”，不是“行为”。

## 3. 总体协作模型

### 3.1 正确模型

正确模型是：

- `Cocos AI` 负责静态 UI 真源
- `Code AI` 负责动态运行时真源
- `Human` 负责局部修饰和最终验收

### 3.2 错误模型

以下模型都是错误的：

1. `Human-first`
   - 人手工搭大部分 UI
   - AI 只做补丁

2. `Code AI-only`
   - 所有 UI 都用 `new Node()` 和 helper 运行时重搭
   - scene / prefab 形同虚设

3. `Double Source of Truth`
   - scene/prefab 里有一套布局
   - 代码里又重写一套布局
   - 最终谁生效靠运气

本规范必须坚持：

> 同一类信息只能有一个真源。

## 4. 职责边界

## 4.1 Cocos AI 的职责

以下内容默认归 `Cocos AI`：

1. scene 结构
2. prefab 结构
3. 节点层级
4. 静态图片引用
5. 静态文字节点
6. 基础位置与尺寸
7. Widget / Layout / UITransform 配置
8. 面板骨架
9. 按钮、标题、图标、背景等稳定 UI
10. 编辑器预览状态

`Cocos AI` 的核心任务不是“把逻辑写进编辑器”，而是：

> 让静态壳在编辑器里可见、可选、可调、可保存。

## 4.2 Code AI 的职责

以下内容默认归 `Code AI`：

1. 游戏状态机
2. 关卡加载
3. bundle 加载
4. main / bootstrap / 微信分包 / 远程数据划分
5. 动态文案
6. 数字刷新
7. 显示隐藏
8. 点击事件
9. 棋盘、豆子、槽位等动态节点
10. 动效与 tween
11. 引导逻辑
12. 平台适配
13. 构建脚本
14. 校验脚本
15. 远程数据 CDN 同步脚本

`Code AI` 的核心任务不是“再造一个 UI 编辑器”，而是：

> 驱动已经存在的 UI 壳，让游戏正确运行。

## 4.3 Human 的职责

以下内容默认归 `Human`：

1. 明确需求
2. 确认优先级
3. 纠正 AI 的设计偏差
4. 在 Cocos 里做局部视觉微调
5. 验收视觉、交互、平台行为
6. 决定哪些改动值得沉淀成规则

Human 默认不应承担：

- 大批量重复摆节点
- 手工复制资源
- 手工维护构建链
- 手工同步大量布局参数

## 4.4 边界判断口径

判断某项需求归 `Cocos AI` 还是 `Code AI`，不要只看“它像不像 UI”，而要看：

1. 这个东西是不是可以预先定义为稳定的视觉基线
2. 这个东西是不是只有运行时计算后才知道结果

推荐口诀：

- **样子先能定下来**：优先归 `Cocos AI`
- **结果要运行时才知道**：优先归 `Code AI`

还要特别避免一个常见误解：

> 不是“只有初始化时的东西才归 Cocos AI”，而是“凡是可预先定义的视觉基线，都应优先归 Cocos AI”。

例如：

1. 一个奖励弹窗不会开局就出现，但它的结构、默认尺寸、动画组件、默认贴图仍然可以由 `Cocos AI` 先做成 prefab
2. 一个面板中的标题不是每次都显示，但标题节点本身、位置和样式仍然归 `Cocos AI`
3. 某个按钮是否可点击归 `Code AI`，但按钮壳、默认图、锚点和对齐仍归 `Cocos AI`

## 4.5 动效归属判断

动效不要笼统地看成一类。默认拆成两种：

### A. Panel FX（面板装饰型动效）

例如：

- 结算页彩带
- 飘带
- 按钮呼吸光
- 奖励弹窗装饰粒子
- mascot 循环展示

特点：

1. 路径和节奏相对固定
2. 更像某个 prefab 的可视组成部分
3. 不强依赖复杂游戏状态

默认规则：

- 可视本体归 `Cocos AI`
- 触发时机、显示隐藏、生命周期归 `Code AI`

### B. Gameplay FX（玩法调度型动效）

例如：

- 棋盘通关扫光
- 豆子飞到槽位
- 插槽扩容后的整体重排动画
- 引导高亮跟随逻辑移动

特点：

1. 目标和顺序依赖运行时状态
2. 数量、时长、范围常随棋盘或数据变化
3. 不适合完全做成固定时间轴

默认规则：

- 全局调度、顺序、时间参数归 `Code AI`
- 单个视觉单元（单格闪光、爆闪、尾迹、粒子）归 `Cocos AI`

一句话：

> Panel FX 更像“面板的一部分”，Gameplay FX 更像“逻辑驱动的视觉单元组合”。

## 5. 单一真源规则

### 5.1 静态 UI 真源

以下信息默认以 `scene/prefab` 为真源：

1. 节点是否存在
2. 节点层级
3. sibling 顺序
4. 节点名称
5. 静态 SpriteFrame 引用
6. 静态 Label 样式
7. 基础位置
8. 基础尺寸
9. 锚点
10. Widget / Layout 配置
11. 基础透明度 / 颜色

### 5.2 动态运行时真源

以下信息默认以代码为真源：

1. 当前金币数
2. 当前体力数
3. 当前关卡号
4. 当前是否显示某面板
5. 当前是否锁定
6. 当前按钮可点击状态
7. 棋盘上的豆子分布
8. 暂存槽内容
9. 引导手势
10. 飞行动画 / 胜利动画 / 失败动画

### 5.3 条件出现的视觉元素

即使某个视觉元素不是“开局就显示”，只要它的以下信息可以提前定义，仍然优先归 `scene/prefab`：

1. 节点结构
2. 默认位置
3. 默认尺寸
4. 动画组件挂载
5. SpriteFrame 或图集引用
6. 层级和挂载点

例如：

- 奖励序列帧效果
- mascot 循环展示
- 成就解锁弹出特效
- 过关庆祝预制体

这些内容的“长什么样”归 `Cocos AI`，而“什么时候出现、播几次、播完怎么回收”归 `Code AI`。

---

## 6. 默认不可覆盖字段

只要某个节点已经由 `Cocos AI` 写进了 scene/prefab，并且没有被明确声明为 `Code AI` 接管，则 `Code AI` 默认**不能覆盖**以下字段：

1. `position`
2. `rotation`
3. `scale`
4. `UITransform.contentSize`
5. `UITransform.anchorPoint`
6. `Widget` 参数
7. `Layout` 参数
8. `Sprite.spriteFrame`
9. `Label.fontSize`
10. `Label.lineHeight`
11. `Label.color`
12. 静态 `Label.string`
13. 静态背景/图标节点层级

例外情况必须满足两个条件：

1. 该节点被明确标注为 `Code-owned`
2. 覆盖行为在代码中有清晰声明，不是“顺手就改”

默认规则：

> 没有明确声明归代码接管的字段，一律视为 Cocos 真源字段。

## 7. Helper 使用规则

### 7.1 Code AI 调用 Cocos 原生能力优先级

`Code AI` 在处理 UI 时，必须遵守以下优先级：

1. 优先复用 scene/prefab 中已存在的节点
2. 优先操作节点上已存在的 Cocos 原生组件
3. 优先调用 Cocos 原生 API
4. 仅在原生组件无法覆盖需求时，才允许增加薄 helper
5. 只有动态临时视觉才允许退回 `Graphics`

优先使用的原生能力包括：

- `UITransform`
- `Widget`
- `Layout`
- `Sprite`
- `Label`
- `Button`
- `Mask`
- `ScrollView`
- `PageView`
- `Prefab.instantiate`
- `assetManager.loadBundle`
- `assetManager.loadAny`

正确顺序应该是：

1. 先问：scene/prefab 里有没有这个节点
2. 再问：节点上已有组件能不能直接解决
3. 再问：Cocos 原生布局组件能不能直接解决
4. 最后才问：要不要写 helper

禁止顺序是：

1. 还没看 scene/prefab
2. 就先写 `drawXXX` / `ensureXXX` / `getOrCreateXXX`
3. 然后用 helper 反过来覆盖编辑器结果

### 7.2 允许的 helper

以下 helper 是允许的，因为它们是“薄封装”：

1. 查找节点
   - `mustFindNode`
   - `findNode`

2. 绑定行为
   - `bindButton`
   - `bindToggle`

3. 更新内容
   - `setLabelText`
   - `setSpriteIfNeeded`
   - `setActiveSafe`

4. 运行时实例化
   - `instantiatePrefab`
   - `loadBundlePrefab`

5. 动态运行时节点
   - 棋盘格
   - 豆子
   - 特效
   - 拖拽中的临时节点
   - 引导高亮

6. 根节点基础设施
   - `ScreenRoot`
   - `PopupRoot`
   - `OverlayRoot`
   - `FxRoot`
   - `BootRoot`

这些 helper 的共同特征是：

> 它们是在帮助调用 Cocos，而不是取代 Cocos。

另外，允许存在的 helper 应该尽量满足以下条件：

1. 输入输出清晰
2. 不偷偷改布局真源
3. 不偷偷改图片真源
4. 不偷偷创建稳定 UI 副本
5. 只是简化调用，不定义新框架

### 7.3 禁止的 helper

以下 helper 类型原则上禁止继续扩张：

1. 运行时把整个稳定按钮视觉重新画出来
2. 运行时把整个稳定面板骨架重新拼出来
3. 运行时自己发明一套布局系统
4. 用 `Graphics` 代替本该存在于 prefab/scene 里的稳定 UI
5. 用 `getOrCreate + forcePosition + forceSize` 长期充当静态布局手段
6. 明明已有 scene 节点，还在代码里再创建一份同名节点
7. 用代码兜底覆盖编辑器里已保存的图片引用
8. 用 helper 替代 `Widget/Layout` 的正常职责
9. 用 helper 长期替代 prefab/scene 的面板骨架职责

一句话判断标准：

- 如果 helper 只是“更方便地用 Cocos”，可以
- 如果 helper 正在“把 Cocos 再实现一遍”，不可以

## 8. 明确禁止的模式

以下模式属于禁止事项：

1. `Code AI` 在稳定 UI 上再造平行布局系统
2. `Code AI` 在 scene/prefab 已存在节点时重新 `new Node()`
3. `Code AI` 无条件覆盖编辑器保存的图片
4. `Code AI` 无条件覆盖人工微调过的位置和尺寸
5. 启动场景直接依赖 CDN / 远程首屏资源
6. 用 fallback 掩盖关键资源缺失
7. 整棵 UI 树 `destroyAllChildren()` 后全部重建
8. 把所有页面都继续塞进一个超大控制器里，不再收敛边界

## 9. scene / prefab / TS / 构建脚本分工

### 9.1 scene 负责

1. 启动场景骨架
2. UI 根节点
3. 首屏可视内容
4. 主菜单稳定节点
5. Loading 稳定节点
6. 全局容器结构

### 9.2 prefab 负责

1. 面板
2. 弹窗
3. 列表项模板
4. 可重复复用的稳定 UI 块
5. 可条件出现的奖励特效骨架
6. 角色类循环展示骨架

### 9.3 TS / JS 负责

1. 运行时逻辑
2. 状态同步
3. 数据绑定
4. 动效
5. 动态节点
6. 面板开关
7. 异步加载
8. scene/prefab 复用逻辑

### 9.4 构建脚本负责

1. Cocos CLI 构建
2. 平台打包
3. bundle 校验
4. 主包大小校验
5. main / bootstrap / 微信分包 / 远程数据边界校验
6. 远程数据 CDN 同步

### 9.5 Preview 资产负责

为了提升 prefab、面板和特效的迭代效率，推荐项目长期保留独立的预览资产：

1. `UIPreview.scene`
2. `PanelPreview.scene`
3. `FxPreview.scene`
4. `PreviewController`
5. mock 状态或 mock 数据注入器

默认分工：

- `Cocos AI` 负责预览场景骨架、预览容器、默认预览节点
- `Code AI` 负责一键触发、状态切换、mock 数据、debug 开关

原则：

> 不要再把“真打一局才能看到某个 prefab 或特效”作为唯一预览方式。

## 10. 推荐分工模板

### 10.1 由 Cocos AI 优先接管

1. 主菜单
2. Loading
3. 设置面板
4. 图鉴面板
5. 排行榜面板
6. 签到面板
7. 商店面板
8. 结算弹窗

### 10.2 由 Code AI 继续接管

1. 棋盘
2. 豆子
3. 槽位动态内容
4. 豆子飞行动画
5. 引导特效
6. 关卡缩放与拖拽
7. 关卡数据加载
8. main / bootstrap / 微信分包 / 远程数据调度

### 10.3 过渡期允许混合，但要带条件

以下情况允许过渡期混合：

1. scene 中先落骨架，运行时再补 SpriteFrame
2. scene 中先落文本节点，运行时再刷新数字
3. prefab 中先存框架，运行时再填列表数据

但要求是：

> 代码只能补动态状态，不能反客为主重写静态骨架。

### 10.4 视觉皮肤系统推荐拆分

如果项目需要做多皮肤系统，推荐使用以下结构：

1. **共享骨架**
   - 一套 gameplay HUD / board / slot / popup 结构
   - 不按皮肤复制十份 scene 或 prefab

2. **皮肤资源包**
   - 每套皮肤只提供资源，不复制整套逻辑结构
   - 典型资源包括：背景、棋盘、格子、插槽、棋子、特效、预览图、局部音效

3. **SkinManager**
   - 由 `Code AI` 管理当前 `skinId`
   - 负责加载皮肤资源、应用资源、刷新运行时表现、持久化和恢复

多皮肤系统的默认约束：

1. 不要做十套完整 gameplay prefab
2. 不要把皮肤系统和 `ThemeChallenge` 混在一个命名空间里
3. 优先做“共享骨架 + 资源替换”，不要先做“结构复制”

关于骨骼动画：

1. 角色、mascot、奖励人物可以考虑骨骼动画或同 rig 换皮
2. 背景、插槽、棋子、格子这类主棋盘换肤，不推荐以骨骼动画作为主方案
3. 主棋盘换肤优先走 `SpriteFrame / Atlas / Material` 替换

### 10.5 棋盘 / 画布手势控制边界

棋盘、拼图、地图、关卡编辑器、画布工具等可缩放区域，应把“内容是什么”和“玩家怎么看内容”拆开。

默认分工：

1. `Cocos AI` 负责：
   - `BoardViewport` / `ContentViewport` 等视口容器的静态节点
   - 棋盘、槽区、顶部栏、按钮、弹窗等稳定 UI 层级
   - 安全区域、默认尺寸、默认锚点、默认可视骨架

2. `Code AI` 负责：
   - 手势状态机
   - `scale / offset` 等运行时视图状态
   - 坐标转换
   - 点击命中
   - 单指拖动
   - 双指缩放
   - PC 滚轮缩放
   - 边界 clamp

3. `Human` 负责：
   - 判断默认手感是否自然
   - 验收不同机型上的点击、拖动、缩放体验
   - 决定是否把某类手势体验沉淀成项目规则

默认结构应该是：

1. 普通 UI 层不跟随棋盘缩放
   - 顶部栏
   - 槽区
   - 技能按钮
   - 弹窗
   - HUD

2. 棋盘内容只进入视口层
   - `BoardViewport`
   - `BoardGroup`
   - `Board`
   - `Pieces`
   - 跟随棋盘缩放的局部特效

默认规则：

1. 不要缩放整个 `Canvas`、`Game` 根节点或整棵玩法 UI 树
2. 棋盘内容的局部坐标应保持稳定
3. 拖动和缩放改变的是视图状态，不是随意重写格子、豆子、拼图块的内部坐标
4. `BoardViewport` / `BoardGroup` 如果由代码接管 `position / scale`，必须明确视为 `Code-owned` 运行时字段
5. 其他静态 UI 节点的 `position / scale / UITransform / Widget / Layout` 仍然遵守第 6 章的不可覆盖规则

手势实现的最低规范：

1. 输入坐标必须先归一
   - `event.getUILocation()` 只适合做移动阈值、双指距离、双指中心等 UI 层判断
   - 单指拖动 delta 应转换到 `BoardViewport` 父坐标系后再相减
   - 点击命中应先转成棋盘内容局部坐标，再转格子坐标

2. tap 和 gesture 必须显式分离
   - 至少区分 `idle / tapCandidate / panning / pinching`
   - 单指移动超过阈值后进入拖动
   - 发生双指缩放后，本轮必须抑制 tap
   - 双指缩放后只松开一根手指时，剩余手指可以继续拖动，但不能触发点击

3. 双指缩放必须固定触点身份
   - 进入缩放时固定两根 `touch id`
   - 后续移动按固定 id 取点
   - 不依赖 `getAllTouches()[0] / [1]` 的数组顺序

4. 缩放必须以手指中心锚定内容
   - 记录双指中心对应的棋盘局部坐标
   - 缩放后反推 offset
   - 保证缩放前手指中心压住的内容点，缩放后仍在手指中心下面

5. 边界 clamp 必须动态计算
   - 根据内容尺寸、当前缩放、安全视口和最小可见区域计算
   - 不要使用只适配某一关或某一机型的固定偏移常量
   - 如果玩法允许局部观察，不要因为棋盘小于视口就强制永远居中

推荐把手势逻辑收敛到一个视口控制模块中，例如：

1. `BoardViewportController`
2. `BoardInputViewportModule`
3. 等价的 `ContentViewportController`

这些模块可以是薄封装，但必须满足：

1. 统一维护 `scale / offset / clamp`
2. 统一提供 UI 坐标、父坐标、内容局部坐标、格子坐标之间的转换
3. 点击、放置、框选、引导、滚轮缩放共用同一套转换口径
4. 不把普通 UI、弹窗、按钮带进棋盘缩放层

反模式：

1. 直接缩放 `Canvas`、`Game` 根节点或整棵 gameplay UI
2. 单指拖动直接用 raw UI 坐标相减更新棋盘节点
3. 双指缩放只改 `scale`，不按手指中心反推 offset
4. 双指缩放后马上允许 tap，导致误选中、误放置
5. 点击、拖动、框选、新手引导各写一套命中转换
6. 边界 clamp 写死 `±300`、`-640` 等一次性常量

一句话：

> 缩放用锚点，拖动用父坐标系 delta，点击用统一命中转换；这些都属于 Code AI 的运行时视图逻辑，但不能破坏 Cocos AI 提供的静态 UI 真源。

## 11. 变更工作流

### 11.1 静态 UI 需求

例如：

- 按钮变大
- 标题挪位置
- 卡片间距调整
- 图标换图

流程必须是：

1. 优先由 `Cocos AI` 修改 scene/prefab
2. Human 在 Cocos 中做局部微调
3. `Code AI` 仅在确有必要时补绑定和动态行为

### 11.2 动态逻辑需求

例如：

- 改选豆子规则
- 关卡加载方式
- 体力恢复逻辑
- 广告解锁逻辑

流程必须是：

1. `Code AI` 修改运行时逻辑
2. 如影响 UI 状态，再同步 `Cocos AI`
3. Human 验证视觉和交互

### 11.3 跨边界需求

例如：

- 某面板既要换布局，又要换交互

流程必须是：

1. 先由 `Cocos AI` 调整静态壳
2. 再由 `Code AI` 接动态行为
3. 禁止同时各自改一半又没有真源声明

### 11.4 Preview 工作流

对于以下内容，推荐默认提供独立 preview 入口：

1. prefab 面板
2. 结算页
3. 奖励特效
4. 失败页
5. 皮肤切换效果
6. 复杂 HUD 状态

推荐工作流：

1. 静态结构先在 Cocos 编辑器中看
2. 动态效果在 `UIPreview.scene` / `FxPreview.scene` 中一键触发
3. 复杂业务状态通过 `PreviewController + mock 数据` 模拟

默认规则：

- 不要依赖“真打通一局/真失败一局”来查看面板和特效
- 需要特定条件才能出现的内容，应优先提供 preview 场景或 debug 入口

### 11.5 动效迭代规则

动效迭代默认先分辨反馈类型，再决定改动最终应该落在 Cocos 资产还是运行时代码中。

#### A. 明确反馈

例如：

- 起点提高 40px
- 摆幅减 30%
- 第 0.2 秒开始加速
- 改成贝塞尔轨迹

规则：

1. 先判断这次改动最终应该落在 Cocos 资产还是代码里
2. 然后直接由对应一侧修改

也就是：

- 改动最终落在 prefab/Animation/粒子参数里 -> `Cocos AI` 改
- 改动最终落在 tween/算法/调度参数里 -> `Code AI` 改

#### B. 模糊反馈

例如：

- 高一点
- 柔一点
- 快一点
- 现在有点死
- 收尾不够干净

规则：

1. 不要直接让 `Code AI` 一轮轮硬猜参数
2. 优先把相关参数暴露到 preview 场景、组件或 `PreviewController`
3. 由 `Cocos AI` 与 Human 在 preview 环境中快速收敛方向
4. 最终再由对应真源一侧固化参数

一句话：

> 明确反馈直接改真源；模糊反馈先变成可调参数，再收敛到真源。

### 11.6 常见需求判定示例

以下示例用于帮助快速判断归属。

#### 示例 A：插槽行与行之间的距离调整

如果需求是：

- “默认视觉上，插槽各行看起来再紧一点”

则判断方法是：

1. 如果这是固定不变的默认视觉节奏，优先归 `Cocos AI`
2. 如果实际行距会随着行数、解锁状态、扩容状态动态变化，最终生效值归 `Code AI`

推荐落法：

- `Cocos AI` 可以定义默认容器、默认参考间距、默认壳体高度
- `Code AI` 负责运行时根据总行数/解锁行数计算真实布局

一句话：

> 固定视觉基线可以交给 Cocos，真正跟状态联动的行距归 Code。

#### 示例 B：点击“添加”后新增一行插槽

这个需求默认归 `Code AI`，因为它牵涉：

- 点击事件
- 是否允许添加
- 消耗条件
- 数据模型变化
- 新增节点或新增数据
- 重新布局
- 动画和存档

`Cocos AI` 在这个需求里负责的只是：

- 添加按钮外观
- 插槽区域容器
- 单行骨架或单格模板

一句话：

> “添加一行”是行为，不是静态布局，因此默认归 Code AI。

#### 示例 C：3 秒奖励序列帧效果

如果需求是：

- “用户完成某个条件后，弹出一个循环播放 3 秒的奖励效果”

推荐拆分是：

1. `Cocos AI` 负责：
   - 把效果做成 prefab
   - 挂好动画组件、默认图集、默认锚点、默认层级
   - 如果有角色展示，也在 prefab 中配置好基础可视结构

2. `Code AI` 负责：
   - 何时触发
   - 挂到哪个 root 下
   - 播一次还是循环
   - 播完后隐藏、回收还是销毁

默认结论：

- 不优先用视频作为这类轻量奖励效果的主方案
- 不优先让 `Code AI` 纯代码临时拼整套序列帧壳
- 优先使用 `prefab + 图集/序列帧资源 + 运行时触发`

#### 示例 D：主题挑战 vs 视觉皮肤

如果项目里已有：

- `theme`
- `theme level`
- `theme groups`

并且它们表示的是“专题关卡/特殊关卡”

则视觉换肤系统必须改叫：

- `skin`
- `skinId`
- `SkinManager`
- `skins.json`

禁止情况：

- 用同一个 `theme` 字段既表示挑战关卡，又表示视觉皮肤

#### 示例 E：风格 vs 皮肤

如果需求是：

- “把整个游戏从休闲风改成可爱风”

这更接近 `Style` 变化。

如果需求是：

- “在同一套玩法结构下切换森林皮肤、猫猫皮肤、糖果皮肤”

这更接近 `Skin` 变化。

推荐规则：

1. `Style` 更大，表示整体美术方向
2. `Skin` 更窄，表示共享骨架上的一套可切换视觉资源
3. 工程上优先建设 `Skin` 系统，不优先建设“全风格实时切换系统”

#### 示例 F：结算页彩带/飘带

如果需求是：

- “彩带起点更高一点”
- “飘动更柔一点”
- “摆幅小一点”

先判断这是不是固定装饰型动效。

如果彩带属于结算 prefab 的固定装饰部分，则：

- 彩带可视本体的改动默认归 `Cocos AI`
- 何时播放、播放几组、胜利和失败是否都播，默认归 `Code AI`

推荐规则：

1. 固定装饰型动效尽量做进 prefab
2. `Code AI` 只负责触发时机和生命周期
3. 不要让 `Code AI` 长期用临时节点+tween 从零重拼整套结算装饰

#### 示例 G：棋盘通关后的分波扫光

如果需求是：

- “从左上到右下，一波一波把所有完成格子闪完”

这类效果默认归 `Gameplay FX`。

推荐拆分是：

1. `Code AI` 负责：
   - 波次分组
   - 顺序计算
   - delay 与总时长
   - 根据棋盘大小、格子数、完成状态做自适应

2. `Cocos AI` 负责：
   - 单格闪光
   - 单格爆闪帧动画
   - 单格粒子或亮环素材

不推荐的方案：

1. 纯固定时间轴做整盘扫光  
   - 因为棋盘大小和完成格子是动态的
2. 纯代码把所有视觉也直接画出来  
   - 因为美术难调、难换皮、难预览

最佳实践：

> `Code AI` 调度全局节奏，`Cocos AI` 提供单元视觉效果。

## 12. 启动、分包与远程数据规则

对于微信小游戏及其他存在首包预算的平台，包体结构必须先按“启动依赖”和“更新频率”拆分，不能把所有非首包内容都塞进一个 Cocos remote bundle。

### 12.1 总原则

1. 启动场景只能引用本地可用资源
2. 首包分层应同时区分：
   - 首屏
   - 首局
   - 非首局
   - 高频动态数据
3. 资源是否进首包，取决于启动依赖级别
4. 资源是否远程化，取决于更新频率和是否需要动态运营
5. 稳定 UI、prefab、图片、音频、特效默认走微信小游戏分包，不走远程热更
6. 远程 CDN 默认只承载关卡 JSON、关卡 manifest 和少量运营配置
7. 启动链路不能隐式依赖 CDN
8. 本地 preview 必须能在不接真 CDN 的情况下完整起首屏和首关

一句话：

> 分包标准看“何时必须拿到”，远程标准看“是否需要脱离微信发版动态更新”。

### 12.2 四层结构

推荐的默认四层为：

1. `main`
2. `bootstrap`
3. 微信小游戏分包
4. 远程关卡数据

#### A. `main`

`main` 只负责启动第一口气，应该尽量瘦。

默认放：

1. 启动 scene
2. 启动脚本
3. 首帧就要反序列化的本地资源
4. 最小 loading cover
5. 平台启动壳必须依赖的资源

默认不放：

1. 首局结算页
2. 排行榜
3. 图鉴
4. 商店
5. 签到
6. 非首帧必需的大图集
7. 仅开发使用的 preview 资产

#### B. `bootstrap`

`bootstrap` 负责“首屏 / 首关本地保障层”。

默认放：

1. 首屏业务继续往下走所需资源
2. 首关 level 数据快照
3. 首局最先会接触到的棋盘/豆子关键资源
4. 首局很可能立刻触达、又不希望依赖远程等待的小型 prefab
5. 首页继续交互所需的小图集、小音效、小面板

典型例子：

1. 首关棋盘数据
2. 首批 bean atlas
3. 首局胜利/失败/继续等结果弹层底板

#### C. 微信小游戏分包

微信小游戏分包负责稳定但非首屏/首关必需的功能资源。Cocos 中应以 Asset Bundle 配置为“小游戏分包”，由入口逻辑按需 `assetManager.loadBundle`。

默认放：

1. 后续功能面板 prefab
2. 稳定 UI 图片、图集、音频、特效
3. 商店、签到、排行榜、设置、图鉴、主题等功能域资源
4. 不需要每日动态更新、但不应进主包/首包的资源

典型例子：

1. `commerce`：商店、签到、体力恢复
2. `leaderboard`：排行榜面板与排行资源
3. `settings`：设置面板
4. `collection`：图鉴/收藏面板
5. `theme`：主题入口与主题面板
6. `audio`：非首局必需音频

禁止事项：

1. 不按每一关拆一个分包
2. 不把每天新增的关卡 JSON 放进微信分包
3. 不把稳定 UI/prefab 默认放到远程 CDN bundle 做热更
4. 不让启动 scene 强引用分包内非首屏资源

#### D. 远程关卡数据

远程 CDN 负责高频动态数据，不负责核心 UI 资源。

默认放：

1. 关卡 manifest，例如 `level_live.json`
2. 分段关卡包，例如 `level_packs/mainline_0001_0100.json`
3. 每日新增关卡包，例如 `level_packs/daily_20260606.json`
4. 难度曲线、关卡投放、活动关卡配置
5. 少量不含脚本、不含核心 prefab 的运营配置

禁止事项：

1. 不放脚本
2. 不放核心 UI prefab
3. 不放稳定通用图片/音频/特效
4. 不把 Cocos remote bundle 作为默认后续资源承载方式

### 12.3 首屏 / 首局 / 非首局 / 动态数据判定

#### A. 首屏

首屏指从应用启动到用户进入第一个可交互页面之前必须拿到的资源。

例如：

1. 启动 loading
2. 第一屏主菜单骨架
3. 启动必须展示的 logo / cover

#### B. 首局

首局指用户进入第一局可玩内容后，高概率在短时间内触达、并且不希望依赖远程等待的资源。

例如：

1. 首关数据快照
2. 首批棋子贴图
3. 首局可能立即出现的结果结算壳
4. 首局失败后立即会用到的继续弹层

#### C. 非首局稳定资源

非首局稳定资源指以下任一情况：

1. 首局不会立刻触达
2. 即使触达也可以接受微信分包异步加载
3. 随客户端版本迭代即可，不需要每日动态更新

这些资源默认进入微信小游戏分包。

#### D. 高频动态数据

高频动态数据指以下任一情况：

1. 每日或高频新增
2. 需要运营后台/关卡生产管线动态投放
3. 可以用 JSON/schema/hash 校验表达
4. 不包含脚本、不包含 Cocos prefab 运行时结构

这些数据默认进入远程 CDN 数据包。

### 12.4 prefab 放置规则

`prefab` 不存在“天然应该进首包”这一说，但稳定 prefab 默认不应放到远程数据层。

规则如下：

1. `prefab` 是否进入 `main / bootstrap / 微信分包`，只由启动依赖级别决定
2. 如果 prefab 被启动 scene 直接引用，它默认会进入本地包
3. 如果 prefab 只在首局高概率触达，但不需要启动场景直连，优先放 `bootstrap`
4. 如果 prefab 不是首局必需，优先放微信小游戏分包
5. 远程 CDN 默认不承载 prefab，除非该项目明确采用远程 Cocos 资源热更方案并另写专项规范

推荐判断顺序：

1. 这个 prefab 是否被启动 scene 直连
2. 这个 prefab 是否首屏立刻可见
3. 这个 prefab 是否首局高概率立刻触达
4. 这个 prefab 是否可以接受微信分包异步加载
5. 这个 prefab 是否真的需要脱离微信发版动态更新

典型例子：

1. 启动 loading 壳：`main`
2. 首局结算弹层底板：`bootstrap`
3. 设置/排行/图鉴/商店 prefab：微信小游戏分包

### 12.5 启动场景强引用链规则

必须特别警惕“启动场景强引用链”。

含义是：

1. 启动 scene 引用了某个组件
2. 组件字段又直连某个 prefab / sprite / audio
3. 该资源就会沿着这条链自动进入本地包

默认规则：

1. 启动 scene 上的字段引用必须极度克制
2. 非首屏必需资源禁止挂在启动 scene 上
3. 首局保障资源如果不需要首场景直连，应从 `main` 下放到 `bootstrap`
4. 非首局稳定资源应进入微信小游戏分包，并通过入口异步加载

一句话：

> 资源进本地包，很多时候不是因为它“重要”，而是因为它被启动场景拉住了。

### 12.6 真源与去重规则

源码层仍然要有清晰真源，但构建产物不应为了“真源完整”而重复下载首包资源，也不应把稳定资源和高频数据混在同一个 remote bundle 中。

推荐规则：

1. 关卡数据真源属于关卡生产管线，发布形态为远程 JSON manifest/pack
2. `bootstrap` 只保留首关快照和启动/首局必需资源
3. 微信小游戏分包保留稳定 UI、prefab、图片、音频、特效
4. 远程 CDN 只保留高频动态关卡数据和少量运营配置
5. 同一逻辑资源如果必须同时出现在 `bootstrap` 与微信分包，必须有自动同步或一致性校验
6. 如果某类资源已经统一为 atlas 或 manifest 管理，旧的单图/单文件副本应从正式构建产物中删除

一句话：

> 真源在源码和自动化规则里，发布产物按 `main / bootstrap / 微信分包 / 远程数据` 去重。

### 12.7 远程关卡数据版本与缓存规则

微信 release 包不应在启动前请求 Cocos remote bundle 版本。远程 CDN 默认只发布关卡数据 manifest 与 pack，且必须支持 schema、客户端版本和 hash 校验。

推荐机制：

1. CDN 根地址保持稳定，例如 `remote_wechat/levels/`
2. `level_live.json` 放在远程关卡数据根目录，并最后上传
3. `level_live.json` 指向当前可用的数据版本和若干 pack
4. release 启动后可后台请求 `level_live.json`，但不能阻塞首屏/首关
5. 进入非首关或高关卡前，按需下载对应关卡 pack
6. 每个 pack 必须有 `id`、`url`、`hash`、`levelRange` 或等价索引
7. manifest 必须有 `schemaVersion` 和 `minClientBuild`
8. 客户端只加载 schema 兼容且满足 `minClientBuild` 的关卡数据
9. JSON pack 上传完成并公网校验通过后，才能最后更新 `level_live.json`
10. 回滚只需要把 `level_live.json` 指回上一数据版本

示例结构：

```json
{
  "manifestVersion": 1,
  "dataVersion": "20260606_001",
  "schemaVersion": 1,
  "minClientBuild": 100,
  "packs": [
    {
      "id": "mainline_0001_0100",
      "url": "level_packs/mainline_0001_0100.json",
      "hash": "..."
    }
  ]
}
```

重要边界：

1. 不把稳定 UI、prefab、图片、音频放进远程关卡数据
2. 不在 `loadCC()` 前阻塞等待 `level_live.json`
3. 不把 `level_live.json` 失败包装成首屏启动失败
4. 不让旧客户端加载需要新代码/schema 的关卡数据
5. 如果新关卡需要新客户端代码，应等待微信新包下载完成，并提示用户“重启小游戏”

一句话：

> 稳定资源随微信版本走分包，动态关卡随 CDN 走 JSON manifest。

### 12.8 preview 资产规则

用于开发调试的 preview 资产，例如：

1. `UIPreview.scene`
2. `PanelPreview.scene`
3. `FxPreview.scene`
4. 仅供调参数或直达触发的 debug prefab

默认规则：

1. 它们可以存在于源码和编辑器工作流中
2. 它们可以用于 plain web preview、本地开发和编辑器验收
3. 它们不应进入正式微信打包产物
4. 如果项目需要平台 debug 包，也应默认排除它们
5. 除非有明确的临时调试 profile，否则 preview 资产不应进入正式 debug/release 包

一句话：

> preview 资产属于开发工具，不属于正式上线内容。

### 12.9 构建变体规则

默认至少区分：

1. 本地 plain web preview
2. 平台 debug 包
3. 平台 release 包

推荐规则：

1. plain web preview 可以包含 preview 场景与 debug 入口，并优先使用本地资源
2. 微信 debug 包默认使用本地/模拟关卡数据，不访问真实 CDN
3. 微信 debug 包默认不包含 preview 资产，除非显式开启调试 profile
4. 微信 release 包使用微信分包承载稳定资源，远程 CDN 只承载关卡数据 manifest/pack
5. 微信 release 包严格不包含 preview 资产
6. debug 和 release 在资源分层规则上应保持一致，不能因为 debug 包就放松主包边界
7. 默认构建命令应是 release，只有显式 debug 命令才开启 debug 诊断逻辑

当前命令口径：

1. `npm run build:wechat`：微信 release
2. `npm run build:wechat:debug`：微信 debug
3. `npm run sync:cdn:wechat`：只允许同步远程关卡数据 release 产物
4. `npm run sync:cdn:wechat:dry`：远程关卡数据 CDN dry-run 验证

### 12.10 构建校验规则

涉及 `main / bootstrap / 微信分包 / 远程数据` 的项目，构建脚本至少应校验：

1. 启动 scene 没有错误引用 CDN / 远程首屏资源
2. `main` 是否只包含启动必需
3. `bootstrap` 是否只包含首屏/首局本地保障资源
4. 微信小游戏分包是否包含稳定 UI、prefab、图片、音频、特效
5. preview 资产是否被错误打进正式平台包
6. 主包大小是否满足项目预算
7. 同一逻辑资源在 `bootstrap` 与微信分包中是否仍一致
8. `game.json` / 构建产物是否生成预期微信分包声明
9. `preloadBundles` 是否没有把非首屏分包提前塞进启动链路
10. 远程关卡数据 manifest 是否存在 `schemaVersion`、`minClientBuild`、`dataVersion`
11. 远程关卡 pack 是否有 hash 且能被校验
12. 远程关卡 manifest 是否最后上传
13. 远程关卡数据是否不含脚本、prefab、稳定 UI 图片或音频
14. CDN 同步 dry-run 是否能验证 manifest 指向的 pack 都存在
15. 旧 Cocos remote bundle 方案是否没有回流为默认构建路径

重要规则：

1. 如果产品预算目标是 2MB，则构建校验阈值也必须按 2MB 左右收紧
2. 不能让“脚本通过但超出真实产品预算”的状态长期存在

### 12.11 默认检查顺序

推荐顺序：

1. 先看 plain Cocos / web preview
2. 再看小游戏本地 debug
3. 再构建微信 release
4. 再跑远程关卡数据 CDN dry-run
5. 最后同步远程关卡数据并看真机 / CDN

## 13. 验证规范

每次改动后至少验证以下几层：

### 13.1 Cocos 编辑器

1. 节点是否可见
2. 节点是否可选
3. 位置尺寸是否可调整
4. 图片替换是否能保存

### 13.2 Codex 自测责任

在 AI-first 工作流里，不能把“自测”默认外包给 Human。

默认要求：

1. `Code AI` 每次完成用户可见改动后，必须先做一轮自测
2. `Human` 负责最终验收，不负责替 `Code AI` 补基础 smoke test
3. 如果只跑了脚本、没跑用户可见链路，不能声称“已验证完成”
4. 如果浏览器、自定义 preview 或平台环境阻塞了验证，必须明确记录阻塞点，不能把“未验证”包装成“通过”

### 13.3 Codex 自测工具优先级

对于当前这类 `Cocos Creator + localhost preview` 项目，推荐按以下顺序选择 Codex 自测工具：

1. `Browser` 插件
2. `playwright` skill
3. `Chrome` 插件

默认规则：

1. 本地 `localhost / 127.0.0.1 / file preview` 优先用 `Browser`
2. 需要沉淀成固定回归脚本的流程，优先补到 `playwright`
3. 只有在依赖真实浏览器登录态、已有标签页、扩展或特定 profile 时，才优先用 `Chrome`

一句话：

> `Browser` 负责日常 smoke，`playwright` 负责可重复回归，`Chrome` 负责真实用户环境复现。

### 13.4 Browser 本地 smoke 规范

对于本地 plain web preview，默认使用 `Browser` 插件，而不是手工口头描述“理论上应该能跑”。

1. 是否能正常启动
2. 是否能进入正确页面
3. 是否出现 runtime error
4. scene/prefab 调整是否生效

推荐动作：

1. 用新标签页打开目标地址，或在 reload 前记录本次开始时间
2. 抓取当前页面截图
3. 读取 console `error / warn`
4. 只按本次加载时间窗口判断新增错误，不把历史日志混进本次结论
5. 对用户可见改动做最短闭环验证

本项目默认 smoke 入口：

1. `Home.scene`
2. `Loading.scene`
3. `Game.scene`
4. `UIPreview.scene`
5. `PanelPreview.scene`
6. `FxPreview.scene`

如果改动会影响某个具体入口，则该入口必须被实际打开一次。

### 13.5 playwright 回归规范

以下情况，推荐从 `Browser` smoke 升级为 `playwright` 回归：

1. 流程固定且会反复回归
2. 需要连续点击多个按钮或多个步骤
3. 需要稳定断言面板显隐、按钮状态、文案变化
4. 需要批量验证多个入口或多个 query 参数

默认要求：

1. `playwright` 不替代 `Browser` 的首轮探索
2. `playwright` 更适合“已经稳定、值得脚本化”的流程
3. 如果某个回归路径已经多次手工 smoke，后续应优先沉淀为 `playwright`

### 13.6 Chrome 使用边界

`Chrome` 插件不是本项目本地自测的默认首选，只在以下情况优先使用：

1. 依赖用户登录态
2. 依赖已有 Chrome 标签页上下文
3. 依赖浏览器扩展
4. 需要复现用户真实浏览器环境问题

默认规则：

1. 不要用 `Chrome` 代替 `Browser` 做日常 localhost smoke
2. 不要因为 `Chrome` 更像真实用户环境，就跳过干净环境下的本地验证

### 13.7 变更类型与必跑自测矩阵

#### A. scene / prefab / 静态 UI 改动

至少要跑：

1. `Cocos 编辑器` 可见性与可选性检查
2. `Browser` 打开受影响入口
3. console 无新增 `error`
4. 受影响节点视觉结果与编辑器保存结果一致

#### B. 面板 / 弹窗 / 结算页 / 失败页改动

至少要跑：

1. `PanelPreview.scene` 或等价 debug 入口
2. 打开一次
3. 关闭一次
4. 再打开一次
5. console 无新增 `error`

默认规则：

1. 不要要求 Human 真打一局才能看结算或失败页
2. 这类内容必须提供 preview 或 debug 直达入口

#### C. gameplay HUD / 棋盘 / 槽区 / 技能按钮改动

至少要跑：

1. `Browser` 打开 `Game.scene` 对应入口
2. 能正常进入首关或指定测试关
3. 棋盘、槽区、技能按钮正常出现
4. 基础点击或拖拽链路不报错
5. 如果改动涉及视口或输入，至少验证一次点击、拖动、缩放或滚轮中的受影响链路
6. 顶部栏、槽区、按钮、弹窗不跟随棋盘缩放
7. console 无新增 `error`

#### D. 主题页 / 图鉴 / 商店 / 排行榜 / 签到改动

至少要跑：

1. `Home.scene` 入口可进入
2. 对应面板能打开
3. 核心切页、关闭、返回链路可工作
4. console 无新增 `error`

#### E. 特效 / 引导 / 条件触发内容改动

至少要跑：

1. `FxPreview.scene` 或 debug 入口
2. 一键触发
3. 至少复播一次
4. 触发与回收链路无新增 `error`

#### F. bundle / 启动链 / 构建脚本改动

至少要跑：

1. `npm test` 或等价校验脚本
2. `Browser` 启动本地 preview
3. 验证首屏能起
4. 验证关键 bundle 不缺失
5. 验证 preview 资产未误入正式平台包
6. 再看平台 debug 或真机链路

### 13.8 本项目默认 smoke 清单

如果没有更具体的任务说明，默认至少覆盖以下最小集合：

1. `Home` 能起
2. `Loading` 能起
3. `Game` 能起
4. `PanelPreview` 能起
5. 改动涉及的面板至少打开一次
6. 改动涉及的关闭/返回链路至少走一次
7. console 无新增 `error`

### 13.9 完成判定

只有同时满足以下条件，才可以把“自测完成”写进结论：

1. 影响范围对应的自测入口已经实际打开
2. 用户可见结果已经被确认
3. console 没有新增 `error`
4. 脚本校验已通过，或已明确记录为什么此轮不适用

以下情况不能算完成：

1. 只跑了 `npm test`
2. 只看了代码，没有打开预览
3. 只在编辑器里看过静态状态，没有验证运行时
4. 明知 preview 运行的是旧生成物，却没有明确说明
5. 明知流程需要 `Browser` / `playwright`，却只做口头推断

### 13.10 平台 debug

1. bundle 是否正常加载
2. 首屏是否缺图
3. 远程关卡数据 manifest / pack 路径是否正确
4. 平台特有逻辑是否异常

### 13.11 构建脚本

1. 构建是否成功
2. 校验脚本是否通过
3. 主包大小是否符合要求
4. bundle 边界是否仍然正确
5. preview 场景和 debug 资产是否被排除在正式平台包之外

## 14. 一票否决规则

出现以下情况，改动应视为不合格：

1. Human 在 Cocos 中调好的位置，运行时又被代码无条件改掉
2. scene/prefab 已有图片引用，运行时又偷偷换回默认图
3. 一个稳定面板同时存在 scene 版和代码重建版
4. 启动场景直接依赖 CDN / 远程首屏资源
5. helper 的作用已经演变成“第二套 UI 系统”
6. 为了实现棋盘拖动或缩放，直接缩放整个 `Canvas`、`Game` 根节点或普通 UI 层

## 15. 推荐口径

后续项目中，统一使用以下表述：

- `Cocos AI`：负责 scene / prefab / 静态 UI 真源
- `Code AI`：负责代码 / 动态运行时真源
- `Human`：负责局部修饰 / 纠偏 / 验收

推荐总描述：

> 本规范适用于 AI-first 的 Cocos 工作流：Cocos AI 负责编辑器资产与静态 UI，Code AI 负责逻辑与动态运行时，人类负责局部修饰、方向纠偏和最终验收。

---

## 16. 最终原则

> Cocos AI 负责把东西“放对、摆对、看得见”；  
> Code AI 负责把东西“接上、跑通、动起来”；  
> Human 负责把东西“改准、判对、收口”。
