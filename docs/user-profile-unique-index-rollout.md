# 玩家存档并发建档修复上线说明

## 生效条件

代码恢复逻辑必须与数据库 `user_profile.openid` 的唯一索引配合使用。
仅部署代码但没有唯一索引，仍可能创建重复档案。索引由数据库持续维护，不在游戏启动时扫描全库。

本次保持旧档案 `_id` 不变，未迁移数据，也未改变新手道具数量。
涉及 `getOpenid`、`syncUserState`、`updateUserProfileAssets`，以及仍可调用的旧版 `addBehaviorData` 建档路径。
明确的重复键错误（11000、E11000、duplicate key）触发一次重新读取；其他错误保持失败。
读取发现两份同玩家档案时明确报错，不任意挑选一份。

## 上线步骤

1. 确认目标云环境与客户端一致；检查现有索引定义及状态。
2. 只读检查整个 `user_profile`：按 openid 分组，找出 count > 1；另查缺失、空值或非字符串 openid。必须完整分页或聚合，不用第一页代替全量检查。备份需要处理的记录。
3. 在测试云环境创建 openid 升序唯一索引（建议名称 `openid_unique`，字段仅 openid，unique=true），确认创建成功并已生效。使用实际 SDK 触发并发，核对平台重复键错误可被识别。
4. 验证后协调部署四个云函数。若生产索引尚不存在，应在受控维护窗口内完成最终数据检查、必要的数据修复和唯一索引创建，避免检查后又产生重复记录。索引创建失败或尚在构建中，不宣布修复生效。
5. 已有重复记录不得直接相加资产或删除；依据进度、资产版本、礼物累计、实验归属等证据另行制定恢复方案。清理属于独立的数据变更，不包含在本次代码修改中。
6. 确认生产索引状态，再验证同玩家并发登录/保存/资产更新只产生一份档案；老存档编号不变、资产不重置、实验回执一致、排位可读取。

## 本地验证

`node tests/user-profile-creation-race.test.js`

测试以数据库唯一约束的模拟实现调用实际四个云函数，覆盖不同入口抢先建档、八次并发登录、奖励不叠加、实验回执一致、旧随机 ID、其他错误不吞掉、冲突后无档案不循环重建、历史重复档案拒绝读取、排位档案唯一性检查。
模拟测试不能替代实际数据库索引及云端 SDK 验证。
