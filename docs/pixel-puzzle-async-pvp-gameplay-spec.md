## 本轮体力、门票与段位奖品（2026-09-07，优先于旧版商业化占位）

### 已确认规则

- 每场新排位消耗 **1 体力 + 1 门票**；服务器成功创建对局时一次性扣除，恢复同一对局不再次消耗。体力沿用全局资产及原有 5 分钟恢复 1 点、上限 10 的规则，不另建 PvP 体力。
- 首次开通默认 3 张门票；每天北京时间 00:00 **补足到 3 张**，不是额外累加 3 张，持有上限 3 张。按服务器时间判断跨天；打开大厅或下一次经济操作时惰性刷新，在线大厅到点重新查询。
- 门票不足时，可在大厅补票：每次合格的激励广告或分享奖励 **+1 张**。广告不限日次数，分享每天最多成功领取 **2 次**；上限分别控制，广告不扣分享次数。门票已满时不发起奖励流程。
- 取消/未完成广告或分享不发票、不消耗成功分享次数；开启系统分享面板本身不算成功。复用现有平台奖励流程，只有合格回调后才请求领取。
- 网络失败保留本次门票领取编号，展示“补领已完成奖励的门票”；重试同一编号不会重复发票。未领取授权 10 分钟有效，跨日失效；该有效期与对局恢复窗口不是同一个概念。
- 每个赛季、每个**大段位**手动领取一次奖品，以本赛季最高达到段位解锁，掉段不收回资格。历史赛季领取凭证保留，新赛季重新累计。
- 奖励道具存入现有全局背包，排位中仍然禁用道具和复活。好友挑战继续显示未解锁，本轮不增加好友局消耗规则。

### UI 与服务端契约

- 统一大厅排位卡增加门票余额、“+”补票按钮和体力提示；段位区左侧增加金色“段位奖励”入口。顶部设置保持隐藏，首页仍只有统一像素拼图入口。
- 补票弹窗展示每日补足规则、当前余额、广告按钮、分享已用次数和失败补领入口。奖励弹窗使用彩色段位标志、现有磁铁/刷子图标、金币数量及可滚动条目；缺失图标或云数据明确报错，不显示虚假到账。
- `getEconomy` 返回服务端时钟、下次刷新时间、门票/分享额度、赛季、奖品状态及全局资产快照。
- `beginTicketReward(source, requestId)` 建立幂等领取授权；`claimTicketReward(claimId)` 在事务中发票、增加分享成功次数并记录凭证。授权必须属于当前 OPENID。
- `matchmake` 的对局创建、有效对局锁、扣门票和扣体力放在同一事务内。并发请求返回同一有效对局；任一资源不足或资产版本冲突时不发生部分扣费。已创建但场景加载失败的对局仍然保留，只能恢复，不承诺自动退款。
- `claimRankReward(tier, seasonId, economyRevision)` 同时更新全局金币/背包与赛季领取凭证；重复请求只返回当前资产，不重复应用增量。
- `pvp_profiles` 新增 `ticketDay/tickets/ticketShares/activeRankedMatchId/rewardSeasonId/seasonPeakStars/rankRewardClaims`。新增 `pvp_ticket_claims` 和 `pvp_rank_reward_claims`；后者主键由玩家、赛季、大段位组成。
- 沿用 `user_profile` 资产，新字段 `pvpEconomyRevision` 随排位扣费/发奖递增。客户端先同步现有存档，再提交经济操作；权威快照替换本地余额。`syncUserState` 与 `updateUserProfileAssets` 使用同库事务及版本检查，防止旧存档覆盖刚扣除或发放的资产。

### 上线边界

- 本轮完成本地源码与隔离测试，**未部署云函数、未修改线上数据库、未打包微信版**。发布需协调更新 `pvpService`、`syncUserState`、`updateUserProfileAssets` 与客户端；新增集合禁止客户端直接读写，沿用现有 `user_profile`，不得批量重置玩家资产。
- `PVP_RANK_REWARDS_ENABLED` 生产默认 `false`。已有 PvP 成绩仍缺完整确定性重放验证，开启真实奖品前必须补齐；不能仅因为新领奖事务通过测试就宣称排位不可作弊。
- 现有广告/分享奖励仅有客户端平台回调，没有服务端可独立核验的完成凭证。新接口的归属、限额、过期和幂等保护不等于广告完成防伪；上线需结合平台可用凭证与风控验证。
- 本地 Web 使用明确的预览数据，展示奖品状态但不发放真实奖品或广告/分享门票；真实广告、分享、跨设备资产同步仍须微信体验版验收。
- 旧审查报告中对局 10 分钟过期、完整棋盘恢复、结果权威性等未完成项，不因本轮经济功能而被标记完成。参见 `pvp-implementation-review-20260905.md`。

## 本轮玩法路径修正（2026-09-05）

- PvP 使用原像素拼图的 `zt_level_` 物理关卡与 `theme` 模式，复用原有传送带、拼色、完成格像素块显示；不再使用主线 `level_ / main`。排位特有的禁道具、禁复活、对手 HUD 和结算继续保留。
- 大厅匹配使用闯关卡片实际加载的像素关卡 ID，而非主线存档进度；资源未就绪时不发起新匹配、不回退主线。直接 `?pvppreview=1&level=N` 同样进入像素关卡 N。
- 新对局和录像明确记录 `levelPrefix=zt_level_`、`rulesVersion=pvp-pixel-v2`。云端按关卡 ID、命名空间和版本匹配；旧主线录像不进入新匹配池，旧 active match 不作为新玩法恢复目标。
- 旧对局、成绩和本地记录不做批量删除、不因版本迁移自动扣星。旧版记录不能进入新棋盘；新客户端发现旧云函数返回的主线对局会明确提示更新云函数。
- 上线需同时更新客户端、`pvpService` 与 `deployment-manifest.json` 中的命名空间索引；本轮仅修改本地源码，未部署云端。机器人仍沿用既有模拟器，完整服务端确定性回放、关卡快照校验不因本次路径修正而视为完成。

## 本轮入口与大厅更新（优先于旧版独立排位大厅描述）

- 首页只保留原有“像素拼图”按钮，进入统一大厅；不再额外创建“像素排位”按钮。首页其他玩法入口保持不变。
- 大厅顶部展示当前段位与星级，下方依次为蓝色“闯关模式”和紫金色“排位对战”卡片，再放排行榜、对战记录、玩法规则及灰色“好友挑战 · 未解锁”。
- 闯关模式复用当前像素拼图的 `zt_level_` 关卡、通关顺序、体力检查与启动流程。关卡号和缩略图来自真实数据，不使用示意图中的固定第 8 关。
- 开始闯关不删除未完成排位的持久化记录，也不影响段位。闯关与排位返回首页场景时自动重开统一大厅；大厅左上角返回按钮回到真正首页。
- 排位卡根据云端检查结果显示“开始排位”或“恢复对局”；恢复必须直接核对云端对局，不再只换按钮文案却调用新匹配。无有效对局时提示已结束或过期；检查失败提供重试，不将错误当作空对局。
- 资源或关卡目录失败时明确提示并禁止闯关启动；排位服务失败不阻断闯关。恢复本地时间仅允许同一个 matchId，不能合并其他对局的缓存。
- 服务端当前未返回赛季结束时间，因此本版展示“闯关练习 · 异步竞技”，不虚构赛季剩余天数。
- 本轮不改变服务端过期规则。已确认的 10 分钟恢复窗口仍需后续落地，不能把该规则确认描述成已部署。

## 1. 玩法定位

像素拼图 PvP 是建立在现有 PCH 传送带拼图玩法上的异步竞速模式。两名玩家不需要同时在线，但都使用完全相同的关卡快照、规则版本和初始条件，各自完成一条从 `t=0` 开始的对局时间轴。

本玩法不是实时同步 PvP：当前玩家开局前，对手的终局、进度时间轴和棋盘轨迹必须已经完整生成并冻结。对局中不连接、轮询或预测另一名正在操作的玩家。

系统将两条经过服务端验证的时间轴进行比较：谁先通关谁赢；如果尚无人通关而一方先失败，则先失败的一方输。

玩法目标：

- 为现有单人拼图增加长期竞技目标。
- 通过好友挑战、真人历史成绩和机器人补位保证随时可玩。
- 保持异步模式低网络要求、低等待时间的优势。
- 保存合法、可复现的玩家操作轨迹，服务机器人训练与难度分析。
- 通过段位、星级、赛季和战绩形成持续成长体验。

## 2. 核心设计原则

1. 公平：双方必须面对同一份不可变关卡。
2. 异步：玩家不需要同时在线，服务器比较两条独立时间轴。
3. 可验证：客户端显示的时间、胜负和棋盘结果都不是最终权威。
4. 可恢复：退出、断网、杀进程后能够回到同一规则状态。
5. 不卖数值：排位赛禁用道具和广告复活。
6. 不暗改结果：机器人轨迹在匹配时固定，不能根据玩家表现临时放水。
7. 可解释：结算页能说明胜负发生在什么时间、因为什么终局事件。

### 2.1 已确认的产品基线

以下内容是当前版本的硬约束，后续章节、原型和实现均以此为准：

| 项目 | 已确认规则 |
|---|---|
| 核心玩法 | 使用项目现有像素拼图玩法，不采用参考产品的整屏填色玩法 |
| 棋盘 | 双方使用同一不可变关卡快照、随机种子和规则版本 |
| 传送带 | 直接复用现有像素拼图传送带节点、资源、方向和动画节奏 |
| 暂存槽 | PvP 不设置、也不显示额外暂存槽、暂存格、容量数字或扩容入口 |
| 排位道具 | 全部禁用，客户端 UI 不展示，服务端拒绝相关命令 |
| 广告复活 | 禁用，同时禁用广告加时和广告扩容 |
| 胜负 | 谁先通关谁赢；尚无人通关时谁先失败谁输 |
| 对手来源 | 同时支持真人历史成绩、好友挑战和机器人补位 |
| 匹配优先级 | 必须先完成合格真人 replay 搜索；只有没有合格真人时才允许机器人补位 |
| 对手呈现 | 普通排位统一显示为“排位对手”，不展示真人历史/机器人来源；好友局显示“好友挑战” |
| 对战信息 | 常驻显示双方进度和对手棋盘缩略图 |
| 网络模型 | 严格异步；对手成绩在当前玩家开局前已完成并冻结，不做实时同步或局中对手轮询 |
| 段位 | 使用王者体系：青铜、白银、黄金、铂金、钻石、星耀、王者 |

### 2.2 术语统一

- `传送带`：当前像素拼图玩法已有的运动轨道及其承载豆块。
- `传送带堵塞`：现有规则判定无法继续并触发失败的传送带状态。
- `暂存槽`：独立于传送带的额外白色槽位或暂存格；PvP 不存在该 UI 与能力。
- `本地待同步队列`：断网时保存尚未上传的动作数据，只是网络机制，不是玩法暂存槽。
- `对手棋盘缩略图`：只读重放结果，不包含对手传送带和未来动作。

## 3. 模式结构

### 3.1 排位赛

排位赛是核心竞技模式：

- 禁用磁铁、刷子、冻结、扩容等全部道具。
- 禁用广告复活、广告加时和广告扩容。
- 双方初始容量、速度、计时和关卡数据完全一致。
- 影响段位星数、隐藏 MMR、勇者积分和赛季数据。
- 支持真人历史成绩匹配及机器人补位。
- 默认不允许中途更换关卡或重新开始同一场比赛。

### 3.2 娱乐赛

娱乐赛用于低压力体验：

- 可以通过独立规则配置是否允许道具和广告复活。
- 道具库存和广告奖励必须由服务端确认。
- 不改变排位星数和排位 MMR。
- 单独记录娱乐模式胜率，不能混入排位机器人标定数据。
- 可以承载主题玩法、特殊容量、限时规则和赛季活动。

### 3.3 好友挑战

- 发起者选择系统允许的 PvP 关卡并先完成自己的对局。
- 服务端验证并冻结发起者的终局、进度时间轴和棋盘轨迹后，才生成可加入的挑战成绩。
- 发起者在结算页分享挑战卡或挑战码给指定好友。
- 好友在截止时间内接受，并以发起者已冻结的完整成绩作为异步对手完成自己的时间轴。
- 两人不会在同一场挑战中同时进行，也不会读取对方局中的 checkpoint。
- 默认不影响排位段位；后续可以增加“好友排位挑战”独立开关。
- 好友挑战仍必须经过服务端重放，不能相信客户端提交结果。

## 4. 对手类型

### 4.1 真人历史成绩

系统从已经通过服务端校验的真人对局中选择一条冻结成绩作为对手：

- 必须匹配同一 `levelSnapshotId` 和 `rulesVersion`。
- 对手时间轴在玩家开局前已经完成，之后不能改变。
- 保存的是匿名公开资料快照和可验证成绩，不暴露 openid。
- 限制同一轨迹的复用次数和同一对手的重复出现频率。
- 轨迹被风控撤销后，不能继续进入匹配池。

这是异步排位的优先对手来源。

### 4.2 好友指定挑战

对手由分享关系确定，不经过普通 MMR 搜索。挑战双方仍然使用同一比赛清单，胜负规则和服务端校验规则保持一致。

### 4.3 机器人补位

当没有合适的真人历史成绩时，系统选择一条已验证的机器人 replay：

- 只能在真人 replay 候选池搜索为空后补位，不能为了控制胜率跳过可用真人。
- 客户端与真人历史对手共用昵称、头像、段位和“排位对手”呈现，不显示 AI 文案或机器人角标。
- 服务端必须保留真实 `matchType=bot`，供审计、补位率、胜率分层和问题追踪使用。
- 机器人 replay 必须在匹配时固定。
- 行为节奏需包含思考停顿、连续有效操作和速度波动，不能使用匀速百分比动画冒充游戏过程。
- 机器人必须使用正式规则接口完成游戏。
- 机器人不能直接改棋盘、时间、容量和通关状态。
- 机器人强度通过固定题库标定为 Bot MMR。
- 排位使用无道具机器人轨迹。

## 5. 公平比赛清单

每场比赛由服务端创建不可变 `matchManifest`：

```text
matchId
mode
levelSnapshotId
levelContentHash
rulesVersion
schemaVersion
seed
timeLimitMs
conveyorCapacity
allowedProps = []       // 排位固定为空
revivePolicy = none     // 排位固定禁用
acceptDeadline
finishDeadline
participantSlots
```

双方只有在上述竞技字段完全相同的情况下才能比较。正式关卡被修改时必须生成新的快照 ID 和内容 hash，不能用新关卡解释旧比赛。

## 6. 时间轴与胜负规则

### 6.1 虚拟同步时间

虽然玩家现实中先后进行游戏，但结算时将双方时间轴都对齐到：

```text
t = 0：第一次有效棋盘操作或正式倒计时开始
```

这里的“虚拟同步”只是服务端比较两份已完成录像时的时间归一化，不代表两名玩家同时在线，也不包含对手实时数据同步。

使用活跃比赛时间，不直接使用现实世界的开局时间。正常前后台切换、断线和恢复如何计时由统一规则处理，双方必须一致。

### 6.2 终局事件

一方时间轴只能产生一个最终竞技事件：

```text
PASS(timeMs)          通关
DEAD_CONVEYOR_FULL(timeMs)  传送带达到现有规则定义的失败状态
DEAD_TIMEOUT(timeMs)  倒计时结束
FORFEIT(timeMs)       主动退出或超期弃权
INVALID               对局无法通过服务端校验
```

### 6.3 结算算法

基础规则：

1. 双方都通关：`PASS.timeMs` 更小者获胜。
2. 一方通关、一方失败：通关者获胜。
3. 双方都失败：更晚失败者获胜，即先死的一方输。
4. 双方终局时间完全相同：平局。
5. 一方弃权：另一方获胜。
6. 双方都弃权：双方失败，不获得胜星。
7. 系统原因导致无法校验：比赛作废，不扣星。
8. 客户端作弊或非法动作导致 `INVALID`：违规方失败并进入风控。

伪代码：

```text
if A.invalid or B.invalid:
    invalid side loses
else if A.pass and B.pass:
    smaller pass time wins
else if A.pass != B.pass:
    pass side wins
else if A.failed and B.failed:
    larger death time wins
else:
    wait until both terminal or deadline
```

### 6.4 对手先死亡时的体验

对手时间轴若在 42 秒失败，当前玩家达到 42 秒且仍未失败，即可提前宣布获胜，无须强制把关卡完成。为避免玩家在胜利后继续进行的状态混乱，推荐：

- 排位立即停止计时并进入胜利结算。
- 结算页提供“继续完成拼图”，但继续过程不再改变比赛结果。
- 继续完成的数据标记为赛后自由玩法，不进入本局竞技时间轴。

### 6.5 对手先通关时的体验

如果对手在 65 秒通关：

- 玩家在 65 秒之前通关，则玩家获胜。
- 到达 65 秒仍未通关，则立即判负。
- 不需要等到玩家自身死亡或关卡计时结束。
- 结算后可以选择继续练习，但不改变结果。

### 6.6 暂停和离线

排位建议规则：

- 普通设置页不暂停竞技时间。
- app hide 后给予一次短保护窗口，例如 5 秒；超过部分计入时间。
- 网络断开不暂停本地逻辑时间，允许动作进入本地待同步队列后补传。
- 系统电话、平台强制中断等是否保护，由统一策略决定。
- 单场累计后台超过上限，例如 60 秒，按弃权处理。
- 所有保护参数由服务端清单下发，不由客户端决定。

## 7. 单局流程

### 7.1 排位匹配流程

```text
进入 PvP 大厅
→ 点击开始匹配
→ 按模式、版本、关卡池、MMR 搜索真人成绩
→ 无合适真人时选择机器人 replay
→ 服务端生成 matchManifest
→ 客户端加载并校验关卡 hash
→ 双方时间轴从 t=0 对齐
→ 玩家进行拼图
→ 动作增量保存并上传
→ 玩家或对手触发胜负阈值
→ 服务端完整重放验证
→ 结算星级、MMR、积分和战绩
```

### 7.2 好友挑战流程

```text
发起挑战
→ 发起者先完成关卡
→ 服务端验证并冻结发起者成绩
→ 生成并分享挑战卡
→ 好友接受已完成的挑战
→ 好友完成
→ 双方轨迹验证
→ 按时间轴规则结算
```

### 7.3 中途退出

- 短暂退出：保存后允许恢复。
- 主动点击认输：立即产生 `FORFEIT`。
- 超过比赛截止时间：系统产生 `FORFEIT`。
- 本地数据损坏：进入恢复冲突，不直接判输；服务端证据足够时从服务端恢复。
- 无法恢复且确认是客户端异常：比赛作废或补偿，不能伪装成正常完成。

## 8. 段位体系

可见段位采用王者体系：

| 大段位 | 小段位 | 每小段星数 |
|---|---|---:|
| 倔强青铜 | III、II、I | 3 |
| 秩序白银 | III、II、I | 3 |
| 荣耀黄金 | IV、III、II、I | 4 |
| 尊贵铂金 | IV、III、II、I | 4 |
| 永恒钻石 | V、IV、III、II、I | 5 |
| 至尊星耀 | V、IV、III、II、I | 5 |
| 最强王者 | 0 星开始 | 持续累计 |

王者星级称号：

| 星数 | 称号 |
|---:|---|
| 0–9 | 最强王者 |
| 10–19 | 非凡王者 |
| 20–29 | 无双王者 |
| 30–39 | 绝世王者 |
| 40–49 | 至圣王者 |
| 50–99 | 荣耀王者 |
| 100+ | 传奇王者 |

### 8.1 星级变化

- 获胜：增加 1 星。
- 失败：减少 1 星。
- 平局：星数不变。
- 系统作废局：星数不变。
- 青铜段位失败不掉星。
- 小段满星后再次获胜，晋升到上一小段 1 星。
- 0 星失败时下降一个小段，并进入该小段满星状态。

### 8.2 勇者积分

建议保留积分保护：

- 正常完成比赛：+5。
- 获胜：额外 +10。
- 连胜：增加少量奖励积分。
- 违规、作弊、恶意退出：本局不获得积分。
- 达到当前段位保护阈值时，失败优先扣积分而不是掉星。
- 排位积分不能通过广告或付费直接购买。

### 8.3 隐藏 MMR

段位和星数负责展示，隐藏 MMR 负责匹配。两名同段位玩家可能拥有不同 MMR，系统应优先选择真实水平接近的对手。

建议初始值：

```text
初始 MMR：1200
定位赛：5 局
定位赛 K：64
前 30 局 K：40
稳定玩家 K：24
高分段 K：16
```

好友赛和娱乐赛不改变排位 MMR。

## 9. 匹配算法

### 9.1 硬过滤

候选对手必须满足：

- 模式一致。
- 关卡快照一致。
- 规则版本一致。
- 排位均为无道具、无复活。
- replay 校验状态为 `VALID`。
- 未超过复用次数和有效期。

### 9.2 搜索范围

```text
0–3 秒：MMR ±75
3–6 秒：MMR ±125
6–10 秒：MMR ±200
超过阈值：机器人补位
```

异步匹配实际可以在后台快速完成，前台匹配动画建议控制在 2–5 秒。

### 9.3 候选排序

```text
matchCost =
    MMR 差距
  + 重复对手惩罚
  + replay 过度复用惩罚
  + 历史成绩过旧惩罚
  + 机器人惩罚
```

机器人候选应附加适度 cost，让质量合适的真人始终优先。

### 9.4 连败和新手保护

- 前 3 局优先匹配比玩家预测 MMR 低约 150 的对手。
- 第 4–5 局差距缩小到约 75。
- 连续 3 负后，下一局候选中心下降约 100 MMR。
- 连续 5 负后，候选中心下降约 175 MMR，并优先较低难度 PvP 关卡。
- 保护只影响匹配选择，不修改机器人过程和比赛结果。

## 10. 机器人玩法规则

### 10.1 机器人决策

机器人从合法动作中选择：

```text
枚举未锁定连通块
→ 用正式规则模拟每个动作
→ 评估立即归位、颜色完成、传送带堵塞风险和死局风险
→ 根据机器人强度进行搜索
→ 输出规范 SELECT_BLOCK 命令
```

### 10.2 机器人强度

| 档位 | 搜索深度 | 候选宽度 | 行为特点 |
|---|---:|---:|---|
| 新手 | 1 | 1–3 | 只关注立即收益，偶尔选择次优动作 |
| 普通 | 1 | 5 | 能控制基础传送带堵塞风险 |
| 熟练 | 2 | 8 | 能预判短期阻挡和死局 |
| 高手 | 3 | 15 | 有稳定的全局颜色规划 |
| 大师 | 4–5 | 30 | 接近当前规则搜索上限 |

机器人必须在固定评测题库上与不同 MMR 真人成绩比较，得出 Bot MMR，不能由策划直接填写强度。

### 10.3 机器人选择分布

```text
70%：玩家 MMR ±75
15%：比玩家低 75–200
15%：比玩家高 75–200
```

不能保证玩家固定胜率，不能在玩家快输时临时让机器人死亡，也不能在玩家快赢时修改机器人通关时间。

## 11. 对局保存与恢复

保存内容必须覆盖完整权威状态：

- 棋盘当前颜色和锁定状态。
- 入口队列及 ready 边界。
- 全部载位和每个载位的层级。
- 容量、逻辑 tick、剩余时间。
- 已执行动作序号和状态 hash。
- RNG seed 和 step。
- 暂停、后台和网络状态摘要。

本地每个有效操作后写入 WAL；每 5 个操作或 10 秒生成检查点。云端按动作分片增量同步，并在关键状态和退出前上传检查点。

恢复时必须先校验 `matchId、rulesVersion、levelContentHash、lastSeq、stateHash`。不一致时进入恢复冲突，禁止悄悄选择一份数据覆盖。

## 12. 玩家操作数据与机器人训练

记录规范动作而不是屏幕录像：

```text
对局清单
动作序号
动作类型和参数
动作前后 stateHash
逻辑时间
服务端接收时间
服务端重放结论
```

只有满足以下条件的轨迹才能进入训练集：

- 玩家已同意相应用途。
- 服务端能从初始状态完整重放。
- 动作连续且每一步合法。
- 终态 hash 一致。
- 豆豆数量、载位层数和锁定状态满足规则不变量。
- 不属于调试构建、自动 QA、作弊或异常对局。
- 已移除 openid、昵称、头像和其他可识别信息。

排位无道具轨迹和娱乐道具轨迹必须分开，不应训练成同一个默认竞技策略。

## 14. 异常结算

| 异常 | 处理 |
|---|---|
| 对手轨迹服务端校验失败 | 对局作废，玩家不扣星 |
| 玩家轨迹校验失败且确认非法 | 玩家失败并进入风控 |
| 服务端故障无法完成验证 | 保持待结算，恢复后重试 |
| 重复提交 | 返回首次提交结果 |
| 重复结算 | 返回原 settlement，不重复发奖 |
| 客户端版本过旧 | 禁止新开局；旧局按旧规则完成或作废 |
| 关卡 hash 不一致 | 禁止开局并明确报错 |
| 双方完全相同时间 | 平局，不增不减星 |

## 15. 赛季建议

- 每赛季持续 8–10 周。
- 赛季结束保存最高段位、最高星数、胜率和纪念徽章。
- 青铜、白银基本保留。
- 黄金以上进行分段继承。
- 隐藏 MMR向赛季中心软重置，而不是清零：

```text
newMMR = 1200 + (oldMMR - 1200) × 0.65
```

- 新赛季首周扩大真人成绩池容量，机器人补位率单独监控。

MVP 包含：

- 排位赛。

- 真人历史成绩匹配。

## 18. 玩法验收标准

- 双方使用完全相同且不可变的竞技清单。
- 排位赛看不到也无法调用道具和广告复活。
- 双通关时较早通关者获胜。
- 一方通关、一方失败时通关者获胜。
- 双失败时较早死亡者失败。
- 对手终局时间到达后能及时提前结算。
- 真人历史、好友和机器人三类对手均能完成完整闭环。
- 所有结果都能由服务端动作重放独立计算。
- 任意有效操作点杀进程后恢复，最终 stateHash 与不中断一致。
- 重复请求不会重复加星、增加 MMR 或发放奖励。
- 机器人只在真人池无合格记录时补位，轨迹在匹配时冻结，页面不暴露其内部来源。
- 段位、小段、星级、勇者积分和赛季继承行为一致。
- 主线进度、图鉴、经济和现有单人玩法不受 PvP 会话影响。

## 20. 服务端总体方案

服务端继续采用当前微信 CloudBase，但新增独立的 PvP 业务边界：

```text
客户端
  ├─ pvpMatch           创建、匹配、接受、查询
  ├─ pvpSession         开始、恢复、设备 lease
  ├─ pvpAppendActions   批量追加动作
  ├─ pvpCheckpoint      保存恢复检查点
  ├─ pvpSubmitRun       提交终局声明
  └─ pvpHistory         查询结算和战绩
          │
          ▼
    CloudBase 数据库
          │
          ├─ pvpVerifyRun    确定性规则重放
          ├─ pvpSettle       事务式结算
          └─ pvpMaintenance  超时、补偿和清理
```

### 20.1 现有云函数复用边界

| 当前能力 | PvP 中的处理 |
|---|---|
| `getOpenid` | 可以保留登录初始化；每个 PvP 函数仍应自行读取微信上下文 |
| `syncUserState` | 继续保存主线进度、经济、皮肤和图鉴，不保存 PvP 局内状态 |
| `addBehaviorData` | 继续记录大厅、匹配、恢复和结算等产品事件 |
| `addFunnelEvents` | 继续记录 PvP 转化漏斗 |
| `saveLevelRecord` | 结算后可旁路写统计摘要，不作为权威成绩 |
| `leaderboard` | 保留现有主线进度榜；PvP 段位和赛季榜独立建设 |
| `updateUserProfileAssets` | 不直接用于 PvP 发奖；奖励必须来自结算账本 |
| 报表和导出函数 | 可复用聚合模式，但不能把普通埋点当训练轨迹 |

当前部分函数允许在微信上下文缺失时使用客户端 `event.openid`，PvP 正式链路必须移除该 fallback。玩家身份只能来自可信平台上下文，客户端不得指定自己或对手的 openid。

### 20.2 服务端权威范围

客户端可以声明操作、时间和结果，但以下内容只有服务端计算结果有效：

- 玩家是否属于该场比赛。
- 动作是否连续、合法且未重复。
- 排位是否使用了禁用道具或复活。
- 最终棋盘、传送带状态和终局类型。
- 通关或死亡的逻辑时间。
- 胜负、星级、MMR、勇者积分和奖励。
- 真人历史成绩是否能够进入匹配池和训练数据集。

## 21. 服务端数据集合

### 21.1 核心集合

| 集合 | 一条记录代表 | 写入方 |
|---|---|---|
| `pvp_match` | 一场比赛及其不可变清单 | `pvpMatch/pvpSettle` |
| `pvp_participant` | 一名参赛者的会话和终局 | 会话、验证、结算函数 |

| `pvp_bot_replay` | 一条已标定机器人轨迹 | 内部生成任务 |
| `pvp_rating` | 玩家某赛季、某模式的段位与 MMR | `pvpSettle` |
| `pvp_reward_ledger` | 一笔幂等奖励 | `pvpSettle` |

## 23. 动作、检查点与恢复协议

### 23.1 动作分片

每次上传 5–20 条，数据库每个 chunk 最多保存 20–50 条连续动作：

```text

```

单条动作：

```text

row/col              // SELECT_BLOCK 时存在
logicalTimeMs

preStateHash

```

排位命令白名单只有：

```text

PAUSE
RESUME
FORFEIT
```

发现 `USE_BRUSH、USE_MAGNET、USE_FREEZE、EXPAND_CAPACITY、AD_REVIVE、AD_ADD_TIME` 时直接拒绝排位轨迹。

### 23.2 追加校验顺序

`pvpAppendActions` 必须依次检查：

```text
可信身份
→ participant 所有权
→ session lease
→ 比赛状态与截止时间
→ requestId 幂等记录
→ startSeq = lastAcceptedSeq + 1
→ chunk 内 seq 连续且 actionId 唯一
→ 命令和参数白名单
→ 请求动作数与字节大小
→ 条件更新 lastAcceptedSeq
```

重复 `requestId` 返回第一次处理结果；乱序请求返回服务端 `acceptedSeq`，由客户端从缺口重传。

### 23.3 检查点

检查点必须覆盖：棋盘当前色和锁定状态、入口队列、ready 边界、全部载位层、容量、逻辑 tick、剩余时间、RNG step、暂停摘要、`lastSeq` 和 `stateHash`。

保存时做快速结构和守恒检查；最终结果仍从初始清单和动作序列完整重放，不能直接相信客户端检查点。

## 24. 云函数接口

### 24.1 `pvpMatch`

支持 `create、accept、get、cancel、listPending`。创建排位时：

1. 读取可信玩家身份及当前 MMR。
2. 选择已批准 PvP 关卡快照。
3. 查询同关卡、同规则、相近 MMR 的合法真人 replay。
4. 无合适真人时选择已验证机器人 replay。
5. 创建 match 和当前 participant。
6. 冻结对手公开资料和终局成绩。
7. 返回 match manifest，不返回内部身份字段。

### 24.2 `pvpSession`

支持 `start、resume、heartbeat、acquireLease、forfeit`。同一 participant 同时只有一个有效 lease；新设备接管后旧设备写操作全部失败。

### 24.3 `pvpSubmitRun`

客户端提交 `lastSeq、terminalType、terminalTimeMs、finalStateHash`，服务端只把它们记录为声明。确认动作已收齐后，将 participant 从 `PLAYING` 条件更新到 `SUBMITTED`，封口动作流并触发验证。

### 24.4 `pvpVerifyRun`

验证器执行：

```text
读取 match manifest
→ 加载不可变关卡并核对 content hash
→ 使用对应 rulesVersion 创建初始状态
→ 按 seq 加载和执行全部动作
→ 校验每步 pre/post state hash 与不变量
→ 推导真实 terminalType 和 terminalTimeMs
→ 写入 verdict
→ 双方完成后触发结算
```

固定 verdict/error code：

```text
VALID
ACTION_SEQUENCE_GAP
ACTION_NOT_ALLOWED
ACTION_ILLEGAL
LEVEL_HASH_MISMATCH
RULES_VERSION_UNSUPPORTED
PRE_STATE_HASH_MISMATCH
POST_STATE_HASH_MISMATCH
FINAL_STATE_HASH_MISMATCH
STATE_INVARIANT_FAILED
TERMINAL_MISMATCH
```

### 24.5 `pvpSettle`

在单个幂等事务内完成：

```text
检查 match 尚未结算
→ 读取双方 VALID verdict
→ 按终局时间轴计算胜负
→ 更新 match 和 participants
→ 更新隐藏 MMR
→ 更新王者段位、小段、星级和勇者积分
→ 写 reward ledger
→ 生成可匹配真人成绩记录
→ 标记 settlement 完成
```

奖励唯一键建议为 `settlementId + playerId + rewardType`。事务重试不能重复加星、修改 MMR 或发奖。

### 24.6 `pvpMaintenance`

每 5 分钟执行：关闭超时比赛、生成弃权终局、回收 lease、重试卡住的验证、补偿结算账本、重置轨迹每日用量、下架旧规则轨迹和清理过期数据。所有任务必须幂等。

### 24.7 `pvpOpponentState`

为对手进度和缩略图提供最小只读数据：

```text
matchId
opponentParticipantId 的服务端内部映射
sourceType              // 客户端仅 ranked、friend
internalSourceType      // human_history、friend、bot，仅服务端和运营审计可见
confirmedLogicalTimeMs
lockedPixelCount
totalValidPixelCount
progressPercent
boardTimeline           // 历史真人的真实锁定格增量，只返回当前时间可见部分
boardSeed               // 仅补位模拟使用，开局冻结
lastConfirmedSeq
freshness               // 固定为 frozen
terminalType
terminalTimeMs
```

历史真人、机器人和好友挑战都不持续请求对手状态：开局一次性返回已冻结 replay 时间线，客户端按自己的虚拟时间推进只读影子棋盘。接口不得返回正在进行的玩家 checkpoint、对方 openid、经济信息或当前时间之后的动作。

## 25. 共享规则与服务端重放

将规则代码抽成不依赖 Cocos 的共享模块：

```text
shared/pvp-rules/
  BoardState.ts
  PchRulesState.ts
  PvpCommand.ts
  PvpReducer.ts
  SeededRandom.ts
  StateHash.ts
  Invariants.ts
  ReplayVerifier.ts
```

服务端规则模块禁止依赖 `Node、Tween、Sprite、Audio、UITransform、scheduleOnce`。客户端动画只消费规则结果，不能决定豆豆移动、死亡和通关。

共享规则必须提供：

```text
createInitialState(manifest, levelSnapshot)
applyCommand(state, command)
exportState(state)
importState(snapshot)
computeCanonicalStateHash(state)
validateInvariants(state)
verifyReplay(manifest, actions)
```

同一 manifest 和动作序列必须在客户端测试环境与 Node 验证器中产生逐步一致的 hash。

## 26. 服务端实施顺序

### 阶段 A：单玩家可信闭环

1. 固定一个关卡快照和规则版本。
2. 定义 command、snapshot 和 canonical hash。
3. 上传 10 个动作。
4. 保存一次检查点。
5. 杀进程后恢复。
6. 服务端从头重放。
7. 对比客户端和服务端终态 hash。

此阶段未通过前，不开始正式匹配、段位和奖励开发。

### 阶段 B：真人异步对手

1. 将合法真人成绩写入 replay pool。
2. 按关卡、规则和 MMR 查询候选。
3. 冻结对手终局和公开资料。
4. 完成当前玩家时间轴比较。
5. 实现双方 verdict 和唯一 settlement。

### 阶段 C：段位与经济

1. 实现隐藏 MMR 更新。
2. 实现王者段位、星级和勇者积分。
3. 使用事务和 reward ledger。
4. 增加赛季榜与战绩查询。

### 阶段 D：机器人与训练数据

1. 离线生成五档机器人 replay。
2. 使用正式验证器校验并标定 Bot MMR。
3. 接入真人优先、机器人补位。
4. 将授权且合法的真人轨迹脱敏导出。
5. 建立规则版本、数据集版本和模型版本关联。

## 27. 服务端验收标准

- 缺少微信可信身份时立即失败，不接受客户端 openid。
- 越权 participant、无效 lease、乱序和重复动作均不会污染动作流。
- 排位出现任何道具或广告复活命令时拒绝轨迹。
- 关卡 hash、规则版本或 schema 不支持时停止验证，不使用 fallback。
- 客户端声明的终局与服务端重放不一致时不进入结算。
- 所有合法中断点恢复后与连续执行得到相同 state hash。
- 双通关、单通关、双死亡、弃权、平局和作废均有确定性测试。
- 重复提交和并发结算不会重复加星、MMR 或奖励。
- 真人历史池不暴露 openid，且支持撤回授权和风控下架。
- 同一真人轨迹的复用次数、每日次数和对手重复率可控。
- 机器人和真人 replay 使用同一动作协议和验证器。
- 旧 rulesVersion 的已开局比赛可继续验证，不能用新规则解释旧动作。
- PvP 故障可关闭入口且不影响主线存档、经济和现有排行榜。

## 28. UI 设计总纲

玩法边界：PvP 复用项目当前像素拼图核心，不引入参考产品的整屏拼豆填色、逐行加格或磁铁/刷子道具玩法。对局主体仍是当前“不规则像素图案棋盘 + 底部传送带 + 点选归位”结构；PvP UI 只增加对手信息、竞速目标、同步状态与结算表现，不额外增加可见暂存槽。

### 28.1 视觉主题：像素锦标赛

PvP 的视觉身份来自“正在拼合的像素画”和“段位竞技”，而不是通用竞技游戏的金属面板。现有浅蓝灰背景和彩色豆豆继续作为主体；新增一条深蓝紫对战带、像素切角段位徽章和一根终局刻度线，构成 PvP 的识别系统。

记忆点只放在一个位置：顶部对战带。其他区域保持安静，避免与彩色棋盘竞争。

设计原则：

- 棋盘第一：中部和下中部不放常驻文字卡片。
- 核心玩法不换皮：主棋盘节点、格子语义、传送带和失败条件沿用现有 PCH 规则，不能为适配 PvP 效果图改成参考产品玩法。
- 一眼看懂：3 秒内看清自己、对手、剩余时间和胜负临界点。
- 信息克制：正常对局只保留一个顶部主 HUD 和一个微型同步状态。
- 状态有证据：匹配、保存、恢复、验证和结算都有明确状态，不用模糊“处理中”。
- 排位纯净：道具栏和广告入口从布局中移除，而不是置灰保留。
- 竞技一致：普通排位统一显示“排位对手”；内部来源必须真实留存，且不能据此动态修改比赛结果。

### 28.2 色彩令牌

| 名称 | 色值 | 用途 |
|---|---|---|
| 雪幕蓝 `arena-bg` | `#EEF1FF` | 当前游戏背景延续色 |
| 夜赛蓝 `arena-ink` | `#25305D` | 对战带、标题、重要数字 |
| 星耀紫 `rank-violet` | `#6657C8` | PvP 主按钮、段位与时间线 |
| 冠军金 `victory-gold` | `#FFC83D` | 胜利、晋级和关键刻度 |
| 危险红 `danger-red` | `#E94D5F` | 传送带堵塞危险、即将失败 |
| 可用绿 `sync-green` | `#38B96B` | 已保存、连接正常 |
| 中性白 `panel-white` | `#FFFFFF` | 浮层和对战带内容底 |
| 次级灰 `muted-ink` | `#77809D` | 次要说明和历史信息 |

颜色不能单独表达状态；同步、危险、胜负必须同时配合图标或文字。

### 28.3 材质和形状

- 主面板使用 2–4 像素感切角，不使用大量相同圆角卡片。
- 对战带外框像一段未完成像素画：边缘由少量方块缺口构成。
- 段位徽章使用清晰几何轮廓，不照搬现有商业游戏徽章素材。
- 按钮保持现有游戏的柔软高光质感，但 PvP 主按钮使用深紫底和金色短边。
- 阴影只用于浮层层级，棋盘周围不增加大面积辉光。

### 28.4 字体与数字

- 中文正文沿用项目稳定可用的圆体/黑体资源，优先保证微信包体和缺字安全。
- 段位名称使用 600–700 字重，避免夸张描边。
- 时间数字使用等宽数字特性；无法提供等宽字体时，为每位数字使用固定宽度容器。
- 终局时间显示到 `0.1 秒`，详情页可显示毫秒；对局 HUD 不显示过多精度。
- 文案不使用全大写英文标签；普通排位来源统一使用“排位对手”。

### 31.2 匹配文案

- 3 秒后：“正在扩大匹配范围…”
- 匹配服务先完成真人 replay 搜索；若候选为空才进入补位。成功页统一显示“排位对手”，不暴露内部来源。
- 失败：“匹配服务暂不可用，请稍后重试”。

取消匹配必须真正取消尚未创建的比赛；比赛已经创建时改为“退出本场”，并明确是否产生弃权。

玩家可见的对手标签只能是：

- `好友挑战`：指定好友。
- `排位对手`：普通排位对手，内部可能来自已验证真人成绩或兜底模拟轨迹。

服务端、运营后台和分析数据不得丢失真实来源；客户端不展示来源，也不得伪造“当前在线”“正在实时操作”等无法证明的状态。

## 33. 对局 HUD

### 33.1 布局

复用现有 `TopBarGroup`，按参考图拆成三个相互叠放但互不嵌套的视觉层；现有棋盘逻辑和底部传送带位置保持优先。

```text
┌────────────────────────┐
│ ⚙  倍速  [原倒计时]┌──┐│
│   (我)  VS  (对手)│缩││
│  [蓝色名牌][珊瑚名牌]│略││
│  我方 58% ━━━━━━━ │棋││
│  对手 63% ━━━━━━━ │盘││
│                   └──┘│
├────────────────────────┤
│                        │
│        像素棋盘         │
│                        │
│                        │
│                        │
│                        │
│      底部传送带区域     │
└────────────────────────┘
```

720×1280 设计分辨率下，顶部竞技信息区约占高度的 28%；右侧纵向缩略图跨越计时、身份和进度层，主棋盘从双进度条下方进入视野。常驻内容只有：

- 左侧设置按钮。
- 原场景 `TimerWrap/Timer` 倒计时控件，保持既有背景资源、图标和 `mm:ss` 格式，不另建 PvP 计时胶囊。
- 原场景 `PchSpeedButton` 倍速控件，保持可点击、档位显示和会话内持久化。
- 左侧蓝色玩家名牌、圆形头像。
- 中间偏右的珊瑚色对手名牌、圆形头像。
- 两个头像之间的橙色描边 `VS`。
- 我方与对手两条完成进度及整数百分比。
- 对手棋盘缩略图。
- 仅在存档或对手数据异常时出现的微型错误状态。

布局落地要求：

- 不显示旧版 `排位对战` 大标题、段位文字行、目标文案行或包住全部信息的单体卡片。
- 对手缩略棋盘固定在顶部右侧独立圆角框中；身份名牌和双进度条占据左侧约 80% 宽度，并允许在视觉上与缩略图轻度重叠，但不能遮住棋盘内容。
- 自己使用蓝色，对手使用珊瑚红；头像悬浮在名牌上沿，昵称位于名牌下半部。
- 两条进度条上下堆叠、左对齐，轨道和百分比必须持续可读。
- 自己的完成进度也常驻显示，使玩家无需根据棋盘目测双方差距。
- 短屏优先缩短昵称，并等比收缩右侧缩略图；不缩小进度数字到不可读。
- 主棋盘必须以“双进度条实际底边”和“传送带实际顶边”组成的剩余可玩区域为基准居中；全屏透明 HUD 根节点和传送带玩法中未显示的旧暂存槽均不能作为遮挡边界参与安全区计算。
- 顶部功能行中，设置按钮、原生加速按钮与原生计时器必须保持同一视觉中心线；布局按各节点缩放后的实际高度计算，不能简单复用同一个 `top` 数值，也不得挤压双方头像、VS、进度条或右上角对手棋盘缩略图。

排位模式保留原 `PchSpeedButton`，双方都按同一公开规则自由切换；按钮继续驱动当前传送带速度并保存玩家本局档位。胜负、对手冻结时间线和提交时间统一按真实经过时间计算，不能把倍率乘入或除出竞技计时。排位仍移除全部道具、广告复活、扩容和暂存槽节点。

PvP 对局不显示独立暂存槽面板、白色暂存格、暂存容量数字或扩容入口；底部只保留当前玩法必需的传送带区域。

传送带不得为 PvP 单独换皮或重新设计。正式实现必须直接复用当前像素拼图玩法的传送带节点、外框资源、轨道箭头、入口/出口、豆块堆叠方式、运动方向和动画节奏；PvP 层只能控制排位中不允许出现的广告、道具和扩展入口显隐。

### 33.2 终局刻度线

对手终局已冻结时，在时间线上显示一个目标刻度：

- 对手 `PASS 65 秒`：金色旗帜，文案“65.0秒前通关”。
- 对手 `DEAD 42 秒`：红色裂纹，文案“坚持超过42.0秒”。
- 好友挑战发起者尚未生成对手成绩，因此发起者局只写“完成后邀请好友挑战”；接受挑战的好友一定能看到已经冻结的目标终局。

接近目标前 10 秒，刻度线颜色加强一次；最后 3 秒才允许轻微脉冲。不能全程闪烁。

### 33.3 危险提示

- 传送带接近现有规则的堵塞阈值：沿用单人玩法已有的危险反馈，不新增暂存槽容量条。
- 距离失败只剩一个合法操作窗口：传送带边框转红，并出现一次“即将堵塞”。
- 即将到达对手通关时间：中央时间变金色。
- 已超过对手死亡时间：立即冻结竞技输入并进入胜利过渡。

危险反馈不能遮住可点击豆豆，也不能用全屏红色闪烁。

### 33.4 保存和网络

仅在右下角或顶部边缘显示 16–20px 状态：

```text
✓ 已保存
↑ 同步中
! 待同步
× 无法安全保存
```

正常“已保存”在 1 秒后收成图标。无法安全保存时才显示常驻文字，并在达到未同步上限时锁住新的排位操作。

### 33.5 对手进度

对手进度是对局 HUD 的常驻核心信息，定义为：

```text
opponentProgress = 已正确锁定有效像素数 / 有效像素总数
```

显示规则：

- 使用整数百分比，例如 `63%`。
- 进度变化时数字在 150–200ms 内轻微跳变，不播放持续增长动画。
- 100% 后立即切换为 `已通关`，并保留终局时间。
- 对手死亡后切换为 `已失败`，缩略图停在死亡状态。
- 不使用“动作数”推算进度，避免不同连通块大小造成误导。
- 进度只能来自当前玩家开局前已经冻结的服务端验证 replay。

720×1280 设计分辨率下，两条进度轨道位于双方名牌下方，参考宽度 460、高度 22，左侧使用同一基线对齐；我方填充色使用玩家蓝，对手使用珊瑚红。接近通关后可变为冠军金；死亡后停留并加红色断点。

### 33.6 对手棋盘缩略图

缩略图常驻于顶部右侧独立圆角框，推荐大小：

```text
720×1280 设计分辨率：外框 190×276，内部绘制区 164×238
短屏：保持 0.69 左右的宽高比等比缩放，最小宽度 154
长屏：不超过 190×276
```

缩略图只呈现棋盘，不呈现对手的传送带、道具、按钮和文字：

- 保留关卡真实轮廓。
- 正确锁定像素使用其目标颜色。
- 未锁定位置使用当前豆豆颜色的低饱和版本。
- 空位使用半透明深灰蓝。
- 已隐藏槽位仍保留目标像素画结果，和主棋盘规则一致。
- 缩略图不可点击，不注册触摸事件。
- 外框使用白底和 3–5px 淡紫描边；所有普通排位对手使用相同外框，不增加来源角标。

缩略图必须基于棋盘格数据批量绘制，不能把完整对手游戏画面渲染到纹理，也不需要复现飞行、Tween、粒子和传送带动画。

### 33.7 异步同步规则

历史真人：

```text
当前玩家虚拟时间 t
→ 读取对手 replay 中 logicalTimeMs <= t 的动作
→ 在本地只读影子规则实例中重放
→ 更新对手进度和缩略图
```

只能播放到当前虚拟时间，禁止提前展示未来棋盘状态。客户端虽然可以预取压缩数据，但 UI 适配层不能访问未来 observation；服务端最终仍独立判断胜负。

历史真人的缩略图必须消费该真人实际对局记录的 `boardTimeline`。每个时间点只保存自上次采样后新锁定的 `addedCells[row,col,colorId]`；客户端累计 `logicalTimeMs <= t` 的增量得到镜像棋盘。缺少棋盘时间线的旧 replay 不得进入匹配池，不允许根据百分比随便点亮若干格。

机器人补位在匹配创建时，使用同关卡 `BoardModel + PchConveyorRules` 离线执行合法选块、传送及归位，冻结 `actions + progressTimeline + boardTimeline + terminal`。缩略图只显示实际归位格，不再按百分比和种子随机补格；开局后不得读取玩家表现改变节奏或格子。旧对局兼容路径不改写已冻结的轨迹。

好友挑战：

- 发起者完成并由服务端冻结完整 replay 后，好友才允许加入。
- 好友开局时一次性取得发起者的 `progressTimeline + boardTimeline + terminal`。
- 播放规则与历史真人完全相同，只显示 `logicalTimeMs <= 当前玩家时间` 的状态。
- 对局期间不请求好友 checkpoint，不显示在线、新鲜度或“刚刚同步”等实时状态。

### 33.8 展开查看

点击缩略图不得打开全屏棋盘，以免遮挡操作和泄露过多解法。可以在暂停/设置浮层中提供“查看对局信息”，展示更大的只读缩略图、对战关系和已冻结终局目标；打开时必须阻断自己的棋盘输入。

### 33.9 性能约束

- 进度数字最多每 100ms 更新一次。
- 缩略图历史 replay 正常每 250–500ms 重绘一次；只在状态变化时更新纹理。
- 好友挑战和历史真人一样，只在本地冻结时间轴跨过新节点时重绘。
- 复用颜色材质和顶点缓冲，不为每个缩略格创建永久独立特效节点。
- 缩略图更新失败不能阻断自己的主棋盘；显示 `进度暂不可用` 并记录诊断。
- 对手状态数据缺失时禁止用随机或估算值填充。

## 34. 终局过渡

胜负发生时先冻结竞技逻辑，再播放 0.8–1.2 秒短过渡：

- 胜利：目标像素画最后几格被金色光点补齐，顶部对战带向中央合拢。
- 失败：不破坏已完成像素图；时间线在失败刻度处断开，使用短促红色裂纹。
- 平局：双方时间数字并列，紫金两色在中央拼成完整方块。
- 系统作废：不播放失败表现，使用中性浮层说明“不计胜负”。

终局第一阶段保留当前棋盘作为暗化背景，并使用一束偏向胜方的聚光。双方头像牌从左右进入，胜方获得原创像素皇冠；持续 0.8 秒后再进入数据结算，不直接用巨型奖章覆盖棋盘。

强动效只用于这一处。大厅卡片、头像和段位徽章不持续漂浮或闪光。

## 35. 结算页

### 35.1 线框

```text
┌────────────────────────┐
│          胜利           │
│                        │
│ [我+皇冠] VS [对手]    │
│  00:58.2     00:61.7   │
│    你先通关 3.5 秒      │
│                        │
│      永恒钻石 III      │
│      ★★★☆☆  +1星       │
│      勇者积分 +15       │
│                        │
│   [再来一局]            │
│   战绩详情   返回大厅   │
└────────────────────────┘
```

### 35.2 结算文案模板

| 场景 | 主文案 | 解释文案 |
|---|---|---|
| 双方通关且玩家更快 | 胜利 | 你先通关 `{delta}` 秒 |
| 对手死亡，玩家存活越线 | 胜利 | 你坚持超过了对手 |
| 玩家先死亡 | 失败 | 你比对手早失败 `{delta}` 秒 |
| 对手先通关 | 失败 | 对手先通关 `{delta}` 秒 |
| 完全同时间 | 平局 | 你们在同一时间结束 |
| 服务端作废 | 本场不计胜负 | 对局数据无法完成验证 |

失败页不写“再接再厉”式空话，直接说明失败原因和下一步。

### 35.3 晋级表现

星级先更新，再出现段位晋级：旧徽章的像素块拆开，重新组合成新徽章。整个过程控制在 1.5 秒内，可点击跳过；降级只做简短下落，不使用羞辱性破碎动画。

### 35.4 结算两阶段结构

1. `0–0.8秒`：暗化原棋盘、聚光胜方、左右玩家牌与胜负标题，只表达情绪。
2. `0.8秒后`：进入清晰数据页，展示终局时间、胜负原因、星级变化和勇者积分。
3. 主按钮始终只有一个：默认“再来一局”；“战绩详情”和“返回大厅”作为次级入口。
4. 挑战结束但服务端仍在验证时，第一阶段可以播放“完成”而不能提前播放“胜利”。

## 36. 战绩与单局详情

### 36.1 战绩列表

每行只展示：

```text
胜负色条 | 对手头像和标签 | 段位 | 终局时间 | 关卡缩略图 | 时间
```

筛选项：全部、排位、好友、娱乐；不在首屏放复杂数据图表。

### 36.2 单局详情

展示：

- 双方终局类型和终局时间。
- 对手类型：历史真人、好友或 AI。
- 关卡缩略图和规则版本的用户化描述。
- 星级、勇者积分变化。
- 关键节点：开始、进入传送带危险状态、通关/死亡。
- 服务端状态：“结果已验证”或明确异常原因。

不向普通玩家展示 action hash、verifierVersion、内部 MMR 和风控分数。

## 37. 好友挑战 UI

排位大厅开放独立的“好友对战”入口。点击后展示两个互斥动作：

- “去挑战好友”：仅挑战好友已经完成、验证并冻结的成绩。从好友分享卡片进入时自动读取 `pvpChallenge` 挑战码；没有挑战码时引导玩家从分享卡进入，不创建空对局。
- “先玩一局并发起”：按当前系统允许的 PvP 关卡创建挑战，发起者先独立完成；成绩保存后，结算页才开放分享给好友。

面板固定说明“不用同时在线、同一关卡、好友局不影响排位”。好友局不允许玩家切换成实时对战，也不提供“边玩边邀请”的入口。

排位级公平规则固定展示为“无道具、无复活”。挑战卡包含像素图轮廓、发起者段位、剩余时间和“接受挑战”按钮。

好友尚未完成时，状态使用：

```text
正在生成挑战成绩
挑战成绩已冻结
等待好友接受挑战
好友正在挑战已冻结成绩
结果验证中
挑战已结束
```

好友接受前，发起者成绩必须已经完成并冻结；任何页面都不得展示双方正在同时操作或实时同步。

## 38. 弹窗与错误状态

### 38.1 离开确认

设置页中的主操作：

- “继续对战”
- “认输并退出”

文案：“认输后本局立即判负，不能恢复。”不能只写“确定退出吗”。

### 38.2 恢复冲突

```text
标题：对局恢复失败
正文：本地进度与服务器记录不一致，本局暂时不能继续。
按钮：重新获取记录 / 返回大厅
```

不提供“继续使用本地数据”按钮，避免产生不可验证分支。

### 38.3 网络中断

- 本地待同步队列正常：“网络不稳定，操作将在联网后同步”。
- 接近待同步队列上限：“请恢复网络后继续排位”。
- 达到待同步队列上限：锁定输入，显示“对局已暂停，等待同步”。

### 38.4 结果验证

验证通常不应显示独立长页面；超过 2 秒后显示：“正在确认比赛结果”。超过超时阈值后允许返回大厅，结算完成时通过大厅角标和战绩状态通知。

## 39. 适配与安全区域

- 设计基准为竖屏 720×1280，同时验证短屏、长屏和刘海屏。
- 顶部对战带必须位于系统安全区下方。
- 棋盘继续使用现有安全矩形计算，不因 PvP HUD 固定写死 Y 值。
- HUD 高度变化后必须重新计算 board safe viewport，并验证前 100 个目标关卡。
- 触控按钮视觉尺寸可小于命中区域，但主要按钮命中区不小于约 80×80 设计像素。
- 缩放预览中沿用现有统一坐标归一化路径，不能为 PvP 新建平行 hit-test。
- 弹窗打开时阻断棋盘输入；关闭后才恢复。

## 40. 动效、音效与震动

| 事件 | 动效 | 音效/震动 |
|---|---|---|
| 匹配成功 | 双方头像由两侧进入并停住 | 一次短促确认音 |
| 对手目标出现 | 时间线刻度落位 | 轻提示音，无震动 |
| 距目标 3 秒 | 时间数字轻脉冲 | 每秒短音，允许关闭 |
| 获胜 | 像素补齐、金色星进入段位槽 | 胜利音＋一次短震 |
| 失败 | 时间线断开、内容轻降饱和 | 低音，无连续震动 |
| 晋级 | 徽章像素重组 | 独立晋级音＋一次中震 |
| 同步失败 | 图标切换，不摇动整个 HUD | 不播放音效 |

遵循系统静音和游戏音效/震动设置；减少动态模式下取消非必要呼吸、粒子和脉冲。

## 43. UI 验收清单

- 进入对局 3 秒内能理解对手类型和胜负目标。
- 顶部 HUD 不遮挡棋盘，底部不侵占传送带。
- 排位完全不存在道具和广告复活入口。
- 对手 PASS 与 DEAD 使用不同图形、颜色和文案。
- 对手完成百分比和棋盘缩略图在正常对局中常驻可见。
- 历史真人和机器人缩略图只重放至当前虚拟时间，不泄露未来状态。
- 好友挑战明确说明“对手成绩已冻结”，不显示最近同步时间或任何实时在线状态。
- 缩略图不遮挡自己的棋盘和传送带操作区。
- 不同棋盘尺寸和轮廓都能完整缩放进缩略图，不裁掉有效格。
- 普通排位统一显示“排位对手”，好友局显示“好友挑战”，且内部来源字段始终准确。
- 对手临界时间到达时结算表现与服务端结果一致。
- 正常保存状态安静，异常状态清晰且能指导下一步。
- 设置、恢复、验证和离开弹窗不会泄漏点击到棋盘。
- 隐藏 MMR、openid、内部校验信息不出现在 UI。
- 段位、小段、星数和王者称号在大厅、匹配、结算、战绩一致。
- 晋级、降级、平局、作废和机器人异常均有独立视觉状态。
- 720×1280、代表性短屏/长屏及微信真机通过截图和点击验收。
- 前 100 个目标关卡无 HUD/棋盘/传送带重叠。
- 网络中断、待同步、缓存上限、恢复冲突都能复现并验证。
- 减少动态、静音和震动关闭设置得到遵守。

## 44. 参考产品拆解与本项目取舍

本节记录对外部拼豆 PvP 页面结构的学习结果。只学习信息架构、状态表达和交互节奏，不复制其徽章、头像、字体、美术造型、商店商品或品牌配色。

| 参考页面 | 值得保留的模式 | 本项目改造 | 不直接采用 |
|---|---|---|---|
| 排位大厅 | 大段位徽章作为视觉中心；一个开始按钮；奖励和榜单靠边 | 改为“像素锦标赛”蓝紫舞台、像素切角徽章 | 粉色背景、原徽章造型、默认门票消耗 |
| 匹配中 | 红蓝对抗分屏；双方卡片对角布局；中央状态 | 蓝紫/珊瑚斜切，加像素闪电接缝和公平规则条 | 伪造实时在线状态、长时间不可取消 |

| 胜利表现 | 暗化原棋盘、聚光胜方、皇冠和左右玩家牌 | 先情绪过渡，再进入可解释数据结算 | 客户端未验证就宣告胜利 |

| 规则/赛季公告 | 统一弹窗壳、突出标题、单一关闭或领取动作 | 复用同一模态组件，正文左对齐并控制行宽 | 大段居中正文和过密装饰 |

| 排位商店 | 边缘入口、段位解锁预览 | 仅保留未来扩展位 | 广告/分享获票、道具商品直接进入排位 |

## 45. 排行榜、规则和赛季弹窗

### 45.1 排行榜

- 顶部展示当前玩家的段位徽章、段位名和赛季剩余时间。
- 首期页签为“全服榜”和“好友榜”；地区榜只有在地区授权、隐私文案和数据质量均完成后才启用。
- 榜单行展示名次、头像、昵称、段位、星数；前 3 名使用原创像素奖牌，其余使用数字。
- 自己不在当前可视区域时，在底部固定一行；进入可视区域后固定行隐藏，避免重复。
- 排序必须使用服务端快照，并展示最近更新时间；客户端不能自行混排缓存数据。

### 45.2 通用竞技弹窗壳

规则说明、赛季更新、段位奖励说明共用一个竞技弹窗壳：

- 全屏暗化遮罩，点击遮罩不关闭涉及领取/确认的弹窗。
- 顶部像素切角标题牌，右上角唯一关闭按钮。
- 米白正文面板，标题和正文左对齐，正文最大宽度约屏幕 78%。
- 底部至多一个黄色/金色主按钮；纯说明弹窗可以无底部按钮。
- 赛季公告奖励必须先请求服务端领取，成功后按钮变为“已领取”；重复点击返回同一幂等结果。

### 45.3 段位奖励页

- 每个大段位一行，展示原创段位徽章、奖励内容和状态。
- 状态：`可领取`、`已领取`、`未达成`、`待开放`、`待配置`；“去挑战”只导航回大厅，不直接创建比赛。
- 当前可领取行使用金色描边，其余保持安静；不可用按钮不能用强饱和主色。
- 赛季重置后生成新 `seasonId` 奖励账本，历史赛季记录只读。

## 47. 一局排位的完整产品流程

```text
进入 PvP 大厅
→ 读取当前赛季段位和待结算对局
→ 点击开始匹配
→ 服务端选择历史真人 replay 或机器人 replay
→ 返回不可变 matchManifest 与对手公开快照
→ 客户端校验关卡 hash、规则版本和资源完整性
→ 展示对手确认页
→ 加载现有像素拼图棋盘与原传送带
→ 3、2、1 倒计时
→ 双方时间轴从 t=0 开始比较
→ 本地记录动作并分片上传
→ 对手 replay 按当前虚拟时间推进缩略图与进度
→ 本方通关、失败、越过对手终局线或主动认输
→ 冻结竞技输入并提交最终动作
→ 服务端完整重放和结算
→ 返回胜负、原因、星级与勇者积分变化
→ 播放短胜负过渡并展示数据结算
→ 再来一局或返回大厅
```

### 47.1 客户端页面状态

| 状态 | 允许操作 | 禁止操作 |
|---|---|---|
| `LOBBY` | 查看段位、战绩、规则；开始匹配 | 创建局内动作 |
| `MATCHING` | 取消尚未成立的匹配 | 重复开始匹配 |
| `OPPONENT_REVEAL` | 等待自动进入 | 更换关卡、刷新对手 |
| `LOADING` | 取消并返回，不计负 | 在资源/hash 未完成前开局 |
| `COUNTDOWN` | 查看双方信息 | 点击棋盘、操作传送带 |
| `PLAYING` | 使用现有像素拼图合法操作 | 道具、复活、扩容、暂存槽操作 |
| `SYNC_BLOCKED` | 恢复网络、打开设置 | 继续产生无法安全保存的动作 |
| `TERMINAL_LOCAL` | 等待上传和验证 | 继续修改竞技状态 |
| `VERIFYING` | 返回大厅并后台等待 | 提前显示确定胜负或发奖 |
| `SETTLED` | 再来一局、战绩详情、返回大厅 | 重复领取同一结算奖励 |

### 47.2 开局前强校验

以下任一校验失败都必须停止进入排位对局并显示明确错误：

- `levelSnapshotId` 不存在或 `levelContentHash` 不一致。
- `rulesVersion`、`schemaVersion` 或回放协议版本不受支持。
- 当前关卡缺少棋盘数据、传送带资源或首屏必需 PvP HUD 资源。
- 排位清单包含非空 `allowedProps`、非 `none` 的复活策略或暂存槽能力。
- 对手 replay 尚未验证、已过期、已撤回或被风控下架。
- 本地存在同一玩家尚未恢复或结算的冲突排位会话。

禁止使用随机对手数据、默认关卡、占位传送带或客户端估算结果继续比赛。

## 48. 像素拼图 PvP 实现约束

### 48.1 复用现有玩法

- 主棋盘继续由现有 PCH 棋盘和规则层创建，PvP 不维护第二套棋盘逻辑。
- 传送带直接复用现有节点和资源，PvP 不创建 `PvpConveyor` 平行实现。
- PvP 通过模式配置关闭道具、广告复活、扩容和暂存槽相关入口；保留原计时器与倍速控制。
- 进度统计读取权威棋盘状态，不以动画完成数量或客户端视觉节点数量计算。
- 失败事件必须由共享规则层产生，UI 不得根据颜色、格子数量或传送带视觉自行判死。

### 48.2 PvP 展示层边界

建议新增一个薄的 `PvpBattleHud` 展示层，输入仅为：

```text
selfPublicProfile
opponentPublicProfile
selfProgress
opponentProgress
opponentBoardSnapshot
opponentTerminalTarget
logicalTimeMs
syncState
```

该展示层不得：

- 修改棋盘、传送带或规则状态。
- 读取未来 replay 动作。
- 自己推算或提交胜负。
- 创建暂存槽、道具、广告或复活按钮。
- 在缩略图中运行粒子、Tween 或完整对手场景。

### 48.3 模式配置

排位配置至少包含：

```json
{
  "mode": "ranked",
  "propsEnabled": false,
  "reviveEnabled": false,
  "adContinueEnabled": false,
  "speedControlEnabled": true,
  "temporarySlotsEnabled": false,
  "reuseCurrentConveyor": true,
  "opponentProgressVisible": true,
  "opponentThumbnailVisible": true
}
```

这些字段既用于 UI 显隐，也必须映射到服务端允许命令集合；只隐藏按钮而仍接受相关命令不算完成。

### 48.4 最新 UI 基准

- 对局 HUD 基准图：`docs/ui/pvp/pvp-battle-hud-authentic-conveyor-v4.png`。
- 大厅、匹配和结算方向图：`docs/ui/pvp/pvp-flow-concept-v2-original-avatars.png`。
- 效果图用于确认信息层级与视觉方向，实际棋盘和传送带必须以当前 Cocos 场景节点及运行时资源为准。
- 对局验收截图中不得出现独立暂存槽、暂存容量、广告、复活、道具或重新设计的传送带。

## 49. 已落地的 CloudBase MVP（2026-09-03）

### 49.1 云函数与客户端

- 云函数：`cloudfunctions/pvpService`。
- Cocos 客户端：`assets/Scripts/Core/PvpServiceMgr.ts`。
- 云函数统一通过 `action` 路由，当前包含 `getProfile`、`matchmake`、`createFriendChallenge`、`joinFriendChallenge`、`getMatch`、`getActiveMatch`、`saveCheckpoint`、`getOpponentState`、`cancelMatch`、`submitResult`、`getLeaderboard` 和 `getHistory`；另有需维护密钥的 `maintenance` 与仅开发环境可开的 `seedDevelopmentData`。
- 微信小游戏使用现有 `PlatformCloudMgr -> WxCloudMgr` 链路调用；Web 编辑器预览保留明确标记的本地机器人，不把本地结果伪装成云端结算。
- 客户端提交终局类型、用时、进度、动作记录、进度时间线和真实锁定格增量时间线；胜负、段位分与新段位由服务端计算。

### 49.2 首期集合

| 集合 | 主键/关键字段 | 用途 |
|---|---|---|
| `pvp_profiles` | `_id = openid`、`rating`、`gamesPlayed`、胜负统计 | 玩家当前赛季排位状态 |
| `pvp_matches` | 自动 `_id`、双方内部身份、公开快照、关卡、提交和结算 | 对局事实与恢复查询 |
| `pvp_replays` | `_id = matchId_openid`、关卡、终局、动作块、`progressTimeline`、`boardTimeline`、授权字段 | 真人历史对手池和训练原始记录 |
| `pvp_settlements` | `_id = matchId_openid` | 幂等结算账本 |
| `pvp_checkpoints` | `_id = matchId_openid`、逻辑时间、进度、最后动作序号、锁定格、`boardTimeline` | 仅用于当前玩家自己的断线恢复，不作为局中对手状态源 |

客户端永远不应直接读取这些集合；生产权限设置为仅云函数可读写。返回对手信息时只发送公开快照，不返回 `openid`。

### 49.3 必建索引

部署前在云开发控制台建立：

1. `pvp_profiles`: `rankStars DESC, rating DESC`；`rating` 只用于服务端同星排序，不返回客户端。
2. `pvp_replays`: `levelId ASC, rulesVersion ASC, verified ASC, eligibleForMatchmaking ASC, useCount ASC, createdAt DESC`。
3. `pvp_matches`: `challengeCode ASC, matchType ASC`。
4. `pvp_matches`: `playerAOpenid ASC, status ASC, updatedAt DESC`。
5. `pvp_matches`: `playerBOpenid ASC, status ASC, updatedAt DESC`。
6. `pvp_matches`: `status ASC, expiresAt ASC`，供过期对局维护任务使用。
7. `pvp_replays`: `eligibleForMatchmaking ASC, validUntil ASC`，供到期 replay 下架任务使用。

索引缺失属于部署错误，匹配或榜单必须显示失败，不允许悄悄退回伪造云端数据。

### 49.4 当前匹配与机器人规则

- 正式排位先通过 `getRankedLevel` 从每日轮换的 12 个像素关卡中选图，再匹配相同 `levelId / rulesVersion / levelHash`、未过期、复用不足 50 次、完整且通过 `replay-verified-v1` 验证并授权的真人 replay；旧 `structural-v1` 记录不入池。
- 真人按隐藏评分 `±75 / ±125 / ±200` 扩圈，综合评分差、同类关卡表现和使用次数，在前 6 个候选里加权随机；排除最近 10 场出现的录像和作者。真人新手目标评分减 100、连败每次减 50（至多 150），与下述机器人保护参数分开。
- 无合格真人记录时使用 `pch-legal-v3` 策略；本地预览和云端复用同一 TypeScript 策略与像素规则，结果由匹配种子、有效评分和关卡内容 hash 决定，不预设通关时间或胜负。
- 机器人初始参考评分 1200；前 5 局对手有效评分减 250；每次连败再减 100，最多减 300；最终限制在 700–3000。降难度只在下一场生成时生效，不在局内追赶玩家。云端持久化排位连败，本地预览只记录当前会话的局数/连败，重复结算不重复累计；好友赛不影响保护。
- 基础操作间隔为 `(1300 - skill × 800) × complexity` 毫秒，叠加确定性波动和思考停顿；`skill = (有效评分 - 700) / 2300`，complexity 考虑有效格数和颜色数。选块优先释放被占用的目标格，并保留不同熟练度的选块随机性；评分越高不保证每个种子都更快。
- 胜负来自实际规则终态：全部归位通关、规则判定死锁失败、达到关卡原时限超时。传送采用保守的 1 倍速固定时步/半圈回填，不使用玩家倍速，也不宣称与渲染路径和飞行动画逐帧等价。缩略图及进度条按同一份、最多 2 秒批次的真实归位增量显示，绝不提前显示未来格子。
- 云函数自带 205 个像素关卡的最小规则数据及轮换目录。修改关卡/共享规则后执行 `npm run pvp:bot:build`；测试校验六个共享模块及关卡副本。新排位必须提交协议与内容 hash，缺少或不一致时在扣费前报错，不静默兼容旧版新开局。
- 新排位冻结 `playerBRating` 用于当前玩家结算，不从已脱敏的公开资料猜评分。旧对局保留原评分兼容逻辑，不重置进行中的对局；开发模拟真人录像默认不进入生产匹配。
- 真人现已接入原控制器规则事件重放，覆盖真实选择、倍速、入口到达、传送和终态；进度/归位格由服务端计算，保存与结算同事务且不可改写。时间仍有客户端/帧调度容差，不等于完整反作弊或机器学习训练；以 `pvp-human-replay-20260907.md` 的验证与上线边界为准。

### 49.5 王者段位结算

- 展示段位采用：倔强青铜、秩序白银、荣耀黄金、尊贵铂金、永恒钻石、至尊星耀、最强王者、荣耀王者、传奇王者。
- 可见排位使用独立 `rankStars`，隐藏 `rating` 只用于匹配和同星排序；所有公开 profile、榜单和结算响应均不返回 `rating` 或 `openid`。
- 前 5 局为定位赛（K=64），第 6–30 局 K=40，稳定期 K=24，高隐藏分区 K=16；第 5 局完成后按隐藏分映射初始星数，此后胜 +1 星、负 -1 星、平局不变。
- 勇者积分达到 100 时可抵消一次定位赛后的掉星，随后扣除 100，并按完成/胜利/连胜继续累积；好友赛不改变星数、隐藏分或勇者积分。
- 好友局双方都是真人账号时，第二位提交者触发事务，一次更新双方 profile、match 和 settlement ledger。
- 历史真人/机器人对手不会重复修改原对手的既有段位，只更新当前挑战者。

### 49.6 好友异步挑战

1. 发起者创建挑战会话，获得固定关卡与规则版本，并先独立完成对局。
2. 发起者成绩验证通过后进入 `WAITING_OPPONENT`，服务端冻结其 `progressTimeline + boardTimeline + terminal`。
3. 结算页通过小游戏分享 query 携带 `pvpChallenge`；成绩未完成前分享的挑战码不能加入。
4. 好友从分享卡进入后读取挑战码，调用 `joinFriendChallenge`，一次性取得发起者已冻结成绩并开始挑战。
5. 好友提交后服务端直接比较两条完整时间轴并事务结算，不存在双方局中互相等待或进度轮询。
6. 挑战 24 小时过期；本人不能加入自己创建的挑战，一个挑战只能绑定一位好友。
7. 好友对战入口不得因没有分享码而隐藏；没有分享码时仍可发起新挑战，加入路径则明确提示从好友分享卡进入。

### 49.7 上线前仍需完成的安全门槛

当前 MVP 已校验身份归属、参与关系、终局枚举、字段范围、动作数量上限和幂等主键，但尚未把完整 `PchConveyorRules` 确定性重放器部署到云端。因此当前版本适合前后端联调和小流量数据采集，不应直接作为不可作弊的正式排位赛上线。

正式开服前必须补齐：

- 服务端按 `rulesVersion` 完整重放动作并核对棋盘、传送带、终局与状态 hash。
- 只有完整重放通过的记录才置为 `verified=true` 并进入真人匹配池或训练集。
- 失败、缺块、序号跳跃、hash 不一致的记录进入隔离区，不更新正式 rating。
- `trainingConsent` 与 `eligibleForMatchmaking` 分开授权；客户端默认不勾选训练授权，只有玩家明确同意后才调用 `setTrainingConsent(true)`；撤回训练授权不能删除必须保留的对局结算账本。

### 49.8 部署步骤

1. 在目标微信云环境创建上述五个集合并设为仅云函数访问。
2. 建立 49.3 中的复合索引。
3. 上传并部署 `pvpService`，安装云端依赖。
4. 在体验版依次验证：创建 profile、机器人匹配、好友挑战两端提交、重复提交幂等、榜单排序和历史查询。
5. 未完成确定性重放器前使用灰度开关限制为测试用户，不开放正式赛季奖励。
6. 配置强随机 `PVP_MAINTENANCE_TOKEN`；仅测试环境可设置 `PVP_ALLOW_DEV_SEED=true` 并调用种子动作，正式环境必须关闭。
7. 用定时触发器调用 `maintenance`，持续处理 24 小时过期对局与到期 replay；调用失败接入告警，不静默跳过。
8. 发布配置以 `cloudfunctions/pvpService/deployment-manifest.json` 为唯一清单；部署前执行 `npm run pvp:cloudbase:preflight`。脚本只输出凭据是否存在，不打印凭据值；返回非零时禁止继续上传。
9. 本地双账号合同由 `tests/pvp-friend-lifecycle.test.js` 覆盖，正式发布仍必须在体验版用两个真实微信账号复验分享卡进入和 OPENID 隔离。

## 50. 正式对战 UI 落地状态（2026-09-03）

- 机器人、真人历史和好友挑战使用同一套正式对战页面；普通排位统一显示 `排位对手`，好友局显示 `好友挑战`，真实来源只在服务端和内部埋点保留。
- 匹配成功后增加约 1.5 秒对手确认页，使用蓝/珊瑚斜切对抗构图，显示双方头像、段位、星级和公平规则。
- 对局顶部按最新参考图拆成独立层：现有设置入口位于左上，原场景 `TimerWrap/Timer` 保持既有倒计时格式，原 `PchSpeedButton` 保持可操作；蓝色自己名牌和珊瑚色对手名牌横排，86px 圆形头像悬浮其上，橙色 `VS` 位于头像之间；两条 460×22 进度条上下堆叠；右侧使用 190×276 独立对手棋盘框。
