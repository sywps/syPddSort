# 真人历史回放排位：实现与验收

更新：2026-09-07。当前交付为客户端/云函数源码与自动验证；不等于正式环境已发布。

## 已实现的玩家流程

1. 排位大厅增加“允许本局成绩供其他玩家异步挑战”开关，默认关闭，独立于模型训练授权。
2. 正式客户端先请求 `getRankedLevel`；服务端从北京时间每日轮换的 12 个关卡中选择，新手先用较小棋盘组。有合适真人回放的关卡优先。
3. 客户端加载所选 `zt_level_` 并核对内容 hash，然后发起 `matchmake`。关卡不一致直接报错，未扣体力/门票。
4. 服务端优先寻找完整且规则重放通过的真人记录。无合适候选时才生成机器人；读数据库失败不会伪装成“无人可匹配”。
5. 对手进度条和缩略图重放冻结的实际归位格；不改速度，不动态追赶，不假装对方实时在线。
6. 玩家完整通关、死锁或超时后，服务端验证结果、结算和保存录像。若是退出或被对手终局截断，不会成为真人对手。
7. 只有当前挑战者改变段位。录像原作者不会因后来被挑战而再次加减星。

## 回放协议与验证

协议 `pch-events-v1`，验证等级 `replay-verified-v1`。

| 事件 | 服务端验证 |
|---|---|
| 初始化 | 只能初始化一次，手动速度限 1/2/3 倍 |
| 点击 | 在当时棋盘合法选块，颜色和实际移动数量一致 |
| 入带飞行完成 | 必须有待到达的豆豆，不允许提前完成飞行 |
| 传送带帧 | 根据实际传送距离、当时速度、原路径入口/出口运行现有规则 |
| 手动倍速切换 | 只接受 1/2/3；5 倍收尾加速必须由规则状态触发 |
| 终局 | 验证通关/死锁/超时条件，拦截超时后操作、伪造存活及提前成绩 |

客户端记录的是现有 `PchConveyorGameplayController` 真实调用的事件，不是根据进度百分比反推的点击。服务端 `PvpHumanReplay` 使用原 `BoardModel/PchConveyorRules` 重放，生成可信的点击日志、归位时间线与完成度。共同使用原传送带几何常量，含入口提前拾取、入口吸附和回填逻辑。

界面按最多 2 秒批次显示归位增量；批次只能延后显示，不能显示未来格子。0% 的合法失败录像也可以显示空的进度缩略图，不当作资源缺失。

边界：这是规则事件级重放验证，不是可信硬件输入证明，也不能防止玩家使用自动点击或修改客户端自行生成一个合法解法。帧累计模拟时间相对客户端时间容许 250ms 误差，飞行到达容许 34ms，提交不能领先服务器对局时长超过 5 秒；倒计时存在 1 秒调度容差，通关展示终局允许归位后至多 10 秒动画时间。仍需真机测量这些容差，不能称为完整反作弊系统。

## 匹配规则

- 同关卡、同 `pvp-pixel-v2`、同完整内容 hash，且 `completeRun=true`、规则验证通过、允许被挑战。
- 排除自己、开发数据、过期记录、已使用 50 次的录像，以及最近 10 场出现过的录像或原作者。
- 保留通关与合法失败样本，不仅保留最快成绩。
- 真人匹配目标评分：自身评分减去新手前 5 局的 100 分；连败每次再减 50 分，最多减 150 分，下限 700。机器人沿用上一阶段自身保护参数，两者不混用。
- 候选按目标评分 ±75 / ±125 / ±200 寻找，查询相邻 200 分桶；每个关卡最多取最近 100 条候选。
- 综合评分差、同关卡/同棋盘大小分组的历史表现差和使用次数，在最合适的前 6 条中加权随机选取。不是保证玩家输赢，也不改变已匹配对手。
- 个人表现样本保留最近 20 局：通关结合用时、失败结合完成度和存活时长。没有样本时不捏造个人速度。
- 关卡池从现有资源目录按有效格数分三组，每组轮换 4 关。最近 3 个关卡尽量不再选择；新手限定较小棋盘组。跨北京时间零点保留前一天关卡池 5 分钟兼容窗口。
- 关卡池名单的资源有效性已检查；实际难度分类目前是棋盘大小代理，后续应根据真实玩家数据校准，不宣称这些关卡已经完成真人难度标定。

## 数据一致性与恢复

- 新排位只接受新版协议，10 分钟过期；好友邀请仍保留独立的 24 小时生命周期。没有修改已有生产对局或批量重置存档。
- 校验参与者之后才能读取已结算结果，不能用别人的 matchId 保存录像。
- 重试按 SHA-256 请求指纹识别；不同内容重提拒绝。同一份录像只写一次，不能覆盖原记录或重置使用次数。
- 玩家结算、星数变化、结算凭证、完整录像在一个事务内落库；写录像失败整笔回滚。
- 对手使用次数在匹配扣费事务中复查并递增，避免并发超过上限后仍扣费匹配旧候选。
- 检查点保存完整事件前缀；服务端重新计算棋盘和传送带状态，拒绝改写已接受前缀。终局也必须延续这个前缀。
- 恢复时重放检查点，还原实际棋盘、入口队列、传送带堆叠、倍速、已记录操作及剩余时限，不只还原完成格。
- 旧 `structural-v1` 记录不会自动升级，也不会进入新真人池；旧版未验证结果不增加可复用录像。主动放弃明确判负，修复了旧逻辑中“很晚退出可能赢过更早失败的对手”的问题。

## 后台接口与发布

- `getRankedLevel`：返回服务端选定 levelId、levelHash、poolVersion，不扣费。
- `getMatchmakingStats`：维护密钥保护，返回最近 100 条 match 的样本统计，包括真人/机器人占比和各自已结算胜场。明确标记样本口径，不冒充全服历史总量或总体胜率。
- 增加索引 `verified_human_level_rating_created_v1`，字段见 `cloudfunctions/pvpService/deployment-manifest.json`。此次不需要新增集合；现有 PvP 集合仍需服务端写权限保护。
- 发布前运行 `npm run pvp:bot:build` 和 `npm run test:pvp`。部署整个 `pvpService`，包含新增 matcher、验证模块、六个共享生成模块、关卡 JSON 与 catalog；不要只复制 index.js。
- 新客户端与云函数需协调上线。旧客户端新开排位会提示更新；新版访问旧云函数会因缺少接口失败，不静默回落到伪造真人数据。
- 本轮部署预检：源码接口/文件检查通过；部署凭据 `TCB_SECRET_ID/TCB_SECRET_KEY` 未配置。没有上传云函数、建生产索引或自动打包微信。

## 自动验收

- 原控制器与服务器差分验证：第 3、9、21 关，各自覆盖通关与超时，验证棋盘、传送带、入口队列一致；覆盖手动倍速、规则 5 倍、事件前缀恢复。
- 拦截：错误棋盘 hash、非法选块、手动 5 倍、瞬间加速、提前到达、1ms 假通关、旧结构校验录像、过期/开发/自己/重复对手、半局记录。
- 内存云函数端到端：A 完整成绩验证入库 → B 优先匹配 A → B 结算但不改变 A 的段位 → B 下局排除 A；验证未授权不入池、第三方提交拒绝、重提不可变、录像写入故障回滚。
- `npm run test:pvp` 集成 11 组测试（含 205 个关卡机器人规则回放的既有回归）。
- 应用 TypeScript 检查使用 `--skipLibCheck --lib ES2020,DOM` 通过。原始 tsc 命令仍受 Cocos 引擎声明与既有 Promise.finally/Array.includes 库配置问题影响，未改动全局配置掩盖问题。
- 原 `test:pch-conveyor` 总测试仍停在此前已记录的 scaled capacity fallback 断言（现为第 624 行）；没有顺手改动无关的主线容量广告交互。
- 当前 Creator 7456 预览生成目录尚未包含新版规则事件代码；未把旧编译产物的页面当成此次界面/真机验收。正式设备的帧率差异、切后台、断网恢复和长日志上传仍需发布前实测。

## 明确未启用

- 本地 platform-none 预览仍是机器人演示，不伪造“真人历史”；测试夹具只存在 tests 中，没有上传到生产对手池。
- 本轮优先完成排位内的真人回放闭环。普通闯关录像自动采集尚未启用；道具、复活和不同条件的闯关记录不会进入排位池。
- 本轮没有接入机器学习训练，也没有迁移/补造旧真人录像。冷启动时真人池为空是正常状态，需真实玩家完成并授权后逐渐积累。
