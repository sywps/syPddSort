## 统计口径：先保证分母一致

1. 关卡UV通关率：统计期内同模式同关卡进入用户与通关用户的交集 / 进入UV；同一个用户跨天重复进入只算一次。允许期间跨天完成，窗口外结果不计，不是新用户首局或严格逐局转化。
2. 局次通关率：level_record成功记录 /（成功+失败记录），排除abandon/interrupted。结算按客户端endTime选取，行为按服务端timestamp选取，两者不是相同时间来源，不能强行逐日对齐。
3. 全表“人均展示”：在该模式该关有进入记录的用户，其同模式同关卡广告展示PV / 进入UV。广告计数按记录levelId关联，包含各广告入口，不代表广告由此关难度造成。
4. 全表“人均完成”：上述进入队列的ad_finish PV / 进入UV；“观看者人均”：同队列ad_show PV / 该队列有ad_show的UV。无观看者时分母为0，显示数据不可得；有进入但无广告记录，显示观测到的0。
5. 35条带关卡上下文的广告展示没有匹配同模式同关卡进入，未硬除以该关进入UV；仍计入全局1857次，并在核对表单列。全期各关进入UV不可相加当全局UV。
6. 已标记theme或page=theme_level的记录单列主题；main及未标记且非特殊关卡记录归入主线/旧版兼容组。59438条行为缺少gameplayEntryMode，另212条为空；旧版记录不能可靠回溯纯主线/主题，应保留分组不确定性。
7. 本报告按记录levelId汇总，不把它无条件视为稳定的物理关卡配置。关卡配置、版本、用户来源随时间变化时，全期指标是混合结果。

### P0：首关决定整体漏损规模

主线/旧版进入15136 UV，通关861 UV，未匹配通关14275 UV。不能将未通关全部叫主动流失、真实失败或纯流失。首次存入前交互仍应优先，但本轮没有重新读取first_level_funnel，不能把此前首关漏斗比例冒充本期全量结果。
优先校准同模式/关卡尝试的进入、可操作就绪、原始点击、存入和结算链路，再做单变量引导实验。首关人均广告展示仅0.0046次，低频本身不能解释大规模未通关，也不能证明广告对少数用户无影响。

### P1：第3、4关需要区分退出与真实难度

L3为163/333=48.95%，L4为81/146=55.48%；L4已结算107次失败，局次仅45.41%，比只看UV率更能提示过程阻力。先按时间耗尽、槽位满、退出和版本配置拆分，确认主导原因后只调整一个参数。L4广告完成事件/展示事件为12/41=29.27%，还需核对具体广告入口，不能只用加广告补救。

### P1：第22关“最终能过，但过程成本高”信号最明确

26名进入用户中16名通关，UV率61.54%；17胜132负，局次率11.41%；192次进入事件，人均7.38次，50次展示、46次完成，人均展示1.9231次。样本达到20，但仍只支持定位排查及小流量实验，不支持全量大改。
动作：按用户分布、失败原因和配置版本复核，不把多个失败集中于一个用户误当普遍困难；若确认容量或时间为主因，只改对应一个变量。主指标用首次尝试通关率及失败负担，护栏为下一关进入和成熟留存，而非广告PV。

### P2：第300关先核对关卡映射与重复进入

29名进入用户、519次进入事件，UV通关65.52%，局次32.69%，208次失败，58次广告展示。当前LevelRouteService物理关卡ID会截到300，需先核对在线逻辑/物理ID与重复游玩设计，不能直接把17.90次人均进入都叫失败重试。此处仅为静态代码证据，未复现线上映射。

### P3：后段多数关卡只观察

300个主线/旧版关卡中，23个进入UV≥20，105个为5—19，172个不足5；277个关卡样本不足20。小样本的0%或100%都不能驱动大范围改关。283关只有成功结算，没有进入行为，UV通关率和人均广告分母均为数据不可得，而非0%或100%。

## 数据可信度与复核边界

- 共40个日/表分区清单，94098条记录；其中行为88101、结算5990、daily_stat/ad_stat合计7条。分区连续、每个叶分区少于1000条、跨日记录ID无重复。服务端独立总数不可得，非事务快照，迟到补报会改变结果。
- daily_stat十天均为空。ad_stat仅8月31日1条、9月6日5条、9月7日1条，其余为空；全期广告统一采用行为事件，不以这些稀疏汇总数据覆盖。
- 行为表没有sessionId、eventSeq或dedupeKey，不能完成物理广告请求级幂等校验；发现1条额外的完全相同分析字段记录，保留并告警，不擅自删除。不同ID仍可能来自业务重复上报。
- 当前addBehaviorData按服务端Date.now入库且直接add；当前广告调用方在onShow上报ad_show，verified_complete上报ad_finish。源码证据解释事件意图，不证明各历史在线包已正确执行。
- 主线/旧版L1行为表显式失败为0，但结算表有20次失败；主题L1行为有12个通关UV，结算却只有1次成功。旧版模式字段缺失、事件覆盖及不同时间源均需校准，不能将这两张表的局次和UV当同一严格队列。
- 本期未识别内部测试账号、投放计划、新老用户、独立广告请求、收入与配置版本分层；都不得用推测填充。线上记录不等于全部已验证真实自然用户。
- 未通关但无失败只是一类记录状态，不等于没有完成广告补偿的纯流失；广告是否增量帮助通关需事件级关联或随机实验。

## 建议行动与验收

1. 今天：数据与客户端补齐关卡尝试ID、广告attemptId及幂等关联，沿用现有系统，不平行造表。复核模式字段和逻辑/物理关卡映射；同一广告回调重放不新增展示或奖励。先离线验证去重规则，避免误删真实事件。
2. 1—3天：优先定位首关首次操作，随后第4/22关失败原因和广告出口。仅在原因确认后设计一个变量的实验；未确认前不加时、不扩容、不加广告。
3. 本周：对胜利奖励与扩容广告按同版本同入口检查展示、完成、发奖和后续通关。确认技术故障直接最小修复；体验改动用户固定分桶，至少覆盖7天且按真实基线计算样本。
4. 停止/回滚：出现无法点击、误发奖、重复扣费/结算立即关闭改动；数据关联不足先暂停结论。转化、下一关进入和成熟D1为护栏，不能以广告次数增加判胜。
5. 暂不处理：少于5 UV的关卡、未知来源造成的比例差、283关“无分母”及300关尚未解释的映射，不作大规模数值调整。
